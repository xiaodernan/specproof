# Mutation Kill-Rate Measurement Plan (变异杀死率)

Interview metric: 变异杀死率 X% — the fraction of injected mutants that
SpecProof detects, measured by a real run and never hand-estimated.

## 1. Method

One campaign = one target + N mutants + two independent verification channels
per mutant:

1. **Mutant generation.**
   - Offline sample (`scripts/mutation_sample/`): 6 hand-defined mutants
     (operand swap, boundary change, return inversion, 3x constant change)
     loaded from `mutants/manifest.json`. Each mutant is applied as a text
     substitution whose `old` string must occur exactly once — the run fails
     loudly otherwise, so a mutant that silently did not apply is impossible.
   - Real repo: the existing pipeline
     `experiments.mutation.generate_mutants` (the same mutation operators the
     DEEP tier runs in `agent/nodes/run_deep_experiments.py`).
2. **Differential channel (tests).** The target's test suite runs against a
   throwaway copy of the target with the mutant applied (the real target is
   never mutated). Offline: `pytest`; real repo: sandboxed `mvnw test`.
3. **SpecProof verdict channel (contracts).** Offline:
   `spec/contract.py` — the deterministic compilation of `spec/spec.md` —
   executes the mutated module and probes the spec'd behaviors. Real repo:
   `agent.checkers.run_contract_checks(base, mutated_head)`.
4. **Classification per mutant:**
   - `killed` — detected by a test failure OR by the SpecProof verdict;
   - `survived` — every available channel ran and reported clean;
   - `skipped` — no channel could run (checker missing, no pytest/mvnw,
     sandbox unavailable). Skipped mutants are recorded with the reason and
     are never counted as killed.
5. **Baseline gate.** The unmutated target must pass both channels first;
   otherwise the whole campaign errors out instead of producing numbers.

## 2. Formula

    kill_rate = killed / (killed + survived)

`skipped` is excluded from both numerator and denominator and is reported
separately, so unavailable infrastructure degrades the run honestly (more
skipped records) instead of inflating or deflating the score.

## 3. Offline sample — measured result

The bundled sample ships one module with real price-calculation behavior
(bulk discount, free-shipping threshold, tax, plus one deliberately
out-of-spec advisory-tip behavior) and a deterministic spec contract.

| Mutant | Operator | Detected by | Status |
|---|---|---|---|
| M01 | operand_swap (discount x(1-r) -> +(1-r)) | tests + verdict | killed |
| M02 | boundary_change (>= 500.0 -> > 500.0) | tests + verdict | killed |
| M03 | return_inversion (>= -> <=) | tests + verdict | killed |
| M04 | constant_change (threshold 100.0 -> 101.0) | **verdict only** | killed |
| M05 | constant_change (tax 0.08 -> 0.18) | tests + verdict | killed |
| M06 | constant_change (tip 0.15 -> 0.18, out of spec) | — | survived |

Measured: **变异杀死率 83.3%** (5 killed / 1 survived / 0 skipped). M04 is
killed by the SpecProof verdict alone — the tests deliberately avoid the
100.0 boundary, demonstrating that the verdict channel adds detection beyond
the test suite. M06 survives on purpose (out-of-spec, untested behavior): the
sample reports a real coverage gap instead of a rigged 100%.

The number is machine-generated by `python scripts/bench_mutation.py
--offline`; the per-mutant evidence lives in
`docs/eval/mutation-results.json` (records with kill sources, exit codes,
contract violations) and `docs/eval/mutation-results.md`.

## 4. Honest limitations

- **Synthetic sample, not the full repo.** The 83.3% figure is measured over
  6 hand-defined mutants of one tiny module. It is a real, reproducible
  number for the bundled sample — not a claim about whole-repo test strength.
- **Real-repo run is a documented manual step** (needs the demo repo and, for
  the differential channel, mvnw/sandbox):

      python scripts/bench_mutation.py --target demo/spring-backend --mutants 10
      python scripts/bench_mutation.py --target golden-cases/case-01-auth-bypass --repo demo/spring-backend --test-class SpecProofGeneratedTest

  When a channel cannot run there (no Docker, no mvnw), the affected mutants
  are recorded `skipped` with the reason — never faked as killed.
- **Surviving mutants are test weaknesses, not findings** — consistent with
  the product spec ("存活变异体不自动视为 Bug"); the campaign reports them
  as coverage gaps.
- **Static contract checks top out at MAJOR** by Review Court policy; the
  verdict channel contributes detection, not severity escalation.
- **Kill rate is channel-relative**: with only one channel available, the
  rate measures that channel. The JSON reports channel availability per run
  so the number cannot be read out of context.
- Mutation operators are text-level and deterministic; they model a fixed set
  of defect classes (annotation/boolean/null/return for Java, operand/
  boundary/return/constant for the sample), not every possible defect.

## 5. Reproduction

    python scripts/bench_mutation.py --offline
    python scripts/bench_mutation.py --offline --mutants 3
    python -m pytest tests/unit/test_bench_mutation.py -q

Expected offline result: 5 killed / 1 survived / 0 skipped, kill rate 0.833
(83.3%). The unit test locks this matrix, including the verdict-only kill of
M04 and the honest skip path for unavailable checkers.
