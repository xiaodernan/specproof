# SpecProof / SpecCraft 工业化、商业化与完整全栈开发终极指南

版本：1.0

编制日期：2026-08-18

适用仓库：`D:\experim\specproof-clean-clone-gate`

文档性质：现状审计、产品化设计、前后端完整建设方案、复杂能力清单、研发计划、交付与运维指南

## 0. 阅读结论

这份文档不是把一个普通 CRUD 项目包装成“工业级”，也不是把路线图当成已交付功能。它首先根据当前仓库代码给出真实基线，然后给出一条能够逐步交付、能够被测试证明、能够被客户购买和运维团队接管的建设路线。

当前项目的核心价值已经成立：SpecProof 不是普通的代码评论机器人，而是一个独立的 AI 变更验收防火墙。它接收需求、验收标准、代码仓库的 Base/Head 版本和验证档位，将自然语言需求编译为可执行 Contract，在隔离环境中做静态差分、反例测试、运行时差分、数据库状态取证、审查法庭裁决和证据胶囊重放，最后生成需求矩阵、Finding、拒绝通知或可验证的合并证书。SpecCraft 则是配套的自主开发 Agent，负责规划、修改、运行检查和交付前自校验。两者结合后，产品闭环可以表述为：

```text
需求与仓库策略
    -> SpecCraft 规划与实现
    -> SpecProof 独立验收
    -> 证据矩阵 / Finding / Capsule / Certificate
    -> 人工批准或拒绝
    -> 可选 Fix Proposal / PR
    -> 重新验收与审计留痕
```

在本次审计中，已经确认的本地结果是：React/Vite 前端生产构建成功；Python `ruff` 检查成功；严格 `mypy` 检查成功；`tests/unit` 共 627 项全部通过，只有一个 `httpx` 与 Starlette TestClient 相关的弃用警告。没有在本次工作中执行 Windows 安装包构建、Docker 镜像构建、Docker Compose 集成环境和提交/推送操作。因此，后文把“本地已验证”“仓库已有但本轮未重跑”“规划新增”明确分开。

工业化的核心目标不是增加更多模块，而是建立四个稳定闭环：

1. 业务闭环：客户可以提交一次验证任务，看到进度，理解结论，下载证据，完成审批，并把结果回写到 GitHub/GitLab/CI。
2. 证据闭环：每个高等级结论都有来源、版本、执行环境、摘要、可重放步骤和完整性验证，不能靠模型一句话直接升级为阻断结论。
3. 运营闭环：租户、用户、权限、配额、费用、审计、告警、备份、恢复、升级和降级都有明确责任边界。
4. 产品闭环：免费试用、团队版、企业私有化和合规行业版有不同功能包与成本模型，不把所有能力无条件堆给所有用户。

## 1. 项目现状：真正已经拥有的东西

### 1.1 核心仓库结构

核心仓库目录大致分为以下边界：

```text
agent/                  LangGraph 验证图、状态、节点、Worker、契约编译器
agent/checkers/         确定性契约检查器与源码检查器
agent/contracts/        需求解析、Contract 候选编译、人工审批注册表
providers/              LLM Provider 抽象、能力探测、预算、脱敏与降级
retrieval/              BM25 / 混合检索 / 重排接口
storage/                MySQL、MongoDB、Redis、RabbitMQ、MinIO、Elasticsearch
api/                    FastAPI、任务 API、Web API、Webhook、SSE、健康和指标
cli/                    verify、eval、probe、replay、contract、craft、fix、mcp 等命令
evidence/               HTML 报告、证书、拒绝通知、签名与证据链
experiments/             全栈状态差分、源码变异测试
sandbox/                 不可信代码执行隔离与限制
integrations/            GitHub Webhook、Check Runs、评论与外部集成
observability/           OTel、结构化日志、Prometheus 指标
services/control-plane/  Spring Boot 租户、用户、Job 视图、Webhook、Outbox
apps/web/                React 18 + Vite + TypeScript 控制台
infra/                   MySQL 迁移、Prometheus、Grafana、OTel 配置
tests/                   unit、integration、fault、security、验收和基准测试
docs/                    架构、ADR、运维、设计、评测和路线图
```

### 1.2 目前最有产品价值的能力

第一，证据政策是产品灵魂。静态源码分析最多只能到 MAJOR；只有真实跑过的 Base/Head 实验、行为或数据库证据、Head 归因、可重放 Capsule 和足够高的 confidence 才能进入 BLOCKER 候选。没有真实实验的结果必须是 `UNVERIFIED`，不能为了好看强行写成 PASS。这种“宁可不确定，也不伪造确定”的策略是区别于普通 LLM Review 的根本。

第二，可靠任务内核已经覆盖了长任务的关键问题。MySQL 记录业务事实与状态机，事务 Outbox 确保建单与待发送消息同时提交，RabbitMQ 负责可靠传递，Redis 负责租约、幂等、限流和进度流，MongoDB 保存 LangGraph checkpoint，MinIO 保存大对象，Worker 能在崩溃后从断点恢复。这个组合并不是为了追求中间件数量，而是分别满足事实一致性、可靠投递、快速短期状态、分析工件、对象存储和长任务恢复。

第三，P2 契约编译能力把需求变成了可治理对象。`agent/contracts/parser.py` 能解析编号章节、验收标准、禁止变更和优先级；`compiler.py` 负责 Contract 家族映射；`registry.py` 支持 PROPOSED、APPROVED、REJECTED、REVOKED 等生命周期和审计。后续所有验证结论都应引用 Contract 版本，而不是只引用一段不可追踪的原始提示词。

第四，RAG 已经不是简单把 README 粘到 prompt。当前设计有方法级符号分块、Elasticsearch BM25、调用图邻域扩展、混合检索和重排降级语义。未来继续增强时必须保持“没有向量模型也能诚实降级到 BM25+图谱”的能力，不能把一个可选模型服务变成主判定链路的单点故障。

第五，已经有全栈差分实验室、源码级变异测试、Ed25519 证书、GitHub App Check Runs、Webhook 验签、MCP 服务端、结构化日志、OTel 插桩和 React 控制台。这说明项目不是从零开始，而是已经完成了许多高难度技术验证。

### 1.3 当前前端实际形态

`apps/web` 是一个 React 18 + Vite 5 + TypeScript 单页应用，采用轻量 hash 路由，没有引入重量级 UI 运行时。现有页面包括 Login、Dashboard、Jobs、JobDetail、Matrix、FindingDetail、Contracts、Eval、Health。`api.ts` 统一封装了 API Key、REST 请求、SSE 进度流、Capsule 下载和响应类型；FastAPI 在存在 `dist/index.html` 时负责 SPA fallback。

这个前端已经能完成“查看和理解验证结果”的第一版控制台，但它还不是完整商业产品前端。缺口主要在：组织和租户切换、用户邀请、RBAC 管理、仓库连接、提交验证向导、策略编辑器、审批工作流、证据时间线、跨任务搜索、账单与配额、通知中心、系统设置、审计查询、主题和国际化、可访问性、错误边界、前端自动化测试、离线/弱网恢复以及面向不同角色的信息架构。

### 1.4 当前后端实际形态

Python FastAPI 是 Agent Runtime，承担任务创建、查询、取消、摘要、SSE、Web API、健康、指标和 GitHub Webhook。Spring Boot Control Plane 已经出现，承担租户、用户、Webhook、Outbox 和只读 Job View 等企业控制面职责。短期不建议立刻把 Python 重写为 Java 或把所有逻辑搬到 Spring；合理的做法是让 Control Plane 负责身份、租户、策略、集成和商业对象，让 Python Runtime 专注于验证执行、模型调用、沙箱和证据生成，通过稳定事件契约连接两者。

### 1.5 当前真实边界

项目目前最重要的事实不是“目录很多”，而是以下边界：

- 核心验证管线和单元测试成熟度较高，但生产级多租户与商业计费还没有形成完整闭环。
- Web Dashboard 有页面和 API，但不能因为页面存在就宣称已经是成熟 SaaS 控制台。
- API Key 鉴权适合内部或早期团队部署，不等价于 OIDC、SAML、SCIM、短期 Token、设备管理和企业身份治理。
- 证书和 Capsule 能力很有差异化，但证书生命周期、密钥托管、撤销、轮换、组织级验证策略需要产品化。
- Docker 沙箱、Compose、真实中间件测试属于部署与集成验收线，本次没有执行，不能把本地 unit 全绿解释为生产验收全绿。
- Git 工作区当前存在用户未提交的修改和未跟踪文件，任何后续开发都必须保留并单独审阅，不能用清理工作区的方式“整理项目”。

## 2. 工业化产品定义

### 2.1 产品名称与产品线

建议把产品拆成三个可独立解释的产品线：

1. **SpecProof Verify**：独立验收平台。面向研发团队、质量团队、安全团队、平台工程团队和合规团队，验证 AI 或人工 PR 是否满足需求。
2. **SpecCraft Build**：受预算和权限控制的自主开发 Agent。面向内部研发人员，能够从任务到变更再到自校验，但不拥有最终合并签字权。
3. **SpecProof Evidence Cloud / Private**：证据、证书、审计和组织治理产品。Cloud 面向 SaaS，Private 面向金融、政企、医疗、能源等代码不可出域的客户。

### 2.2 目标用户和购买理由

研发负责人购买它，是因为 AI 生成代码的产量上升后，传统 Review 无法覆盖行为回归、权限丢失、事务语义、状态污染和消息重复等问题。

平台工程负责人购买它，是因为他们需要统一接入 GitHub、GitLab、Gerrit、Jenkins、GitHub Actions、Argo Workflows 和内部流水线，并且需要可观测、可限流、可回滚的执行平台。

安全与合规负责人购买它，是因为审计需要回答“哪条需求、哪个版本、哪个证据、哪个环境、谁批准、是否可重放”，而不是一张无法复核的模型评论截图。

企业架构负责人购买私有化版本，是因为源代码、日志、模型请求和证据必须在本地或指定区域保存，且需要接入企业 SSO、密钥系统、对象存储、审计平台和工单系统。

### 2.3 商业包装

建议至少提供四档：

| 版本 | 客户 | 核心范围 | 限制与计费 |
|---|---|---|---|
| Community | 个人和开源项目 | CLI、单仓库、确定性检查器、基础报告 | 本地运行，无 SLA |
| Team | 5-50 人团队 | SaaS 控制台、GitHub App、任务队列、基础 RBAC、共享契约 | 按席位 + 验证分钟/任务量 |
| Enterprise Cloud | 中大型组织 | 多租户、SSO、审计、策略、配额、签名证书、私有连接、SLA | 合同计费，按组织和执行量 |
| Enterprise Private | 高合规和代码不出域客户 | 私有化部署、内网模型、HSM/KMS、数据留存策略、定制适配器 | 订阅 + 实施服务 + 支持等级 |

不要一开始就把“模型 token”直接暴露成主要价格单位。客户购买的是可靠验收能力，模型调用只是成本因素。内部要记录 token、缓存命中、沙箱 CPU、存储空间和验证分钟，用于成本治理；对外可用任务点数、执行分钟、仓库数和并发额度等更易理解的单位。

## 3. 终极目标架构

### 3.1 领域划分

完整商业平台建议拆成以下领域，而不是按“所有类都放 Python”组织：

```text
Identity & Tenant        身份、组织、成员、角色、SSO、SCIM、API Token
Repository Integration   仓库连接、Webhook、分支、Commit、PR、Check Run
Specification            需求、版本、Contract、审批、宪法和策略
Verification             Job、状态机、阶段、预算、并发和取消
Execution                沙箱、Worktree、Maven/Gradle/npm/Python 执行器
Evidence                 Finding、Matrix、Capsule、Certificate、签名和重放
Agent                    SpecCraft 计划、工具调用、记忆、修复建议、审批
Evaluation               金案例、基线、模型评测、回归门禁和报告
Billing & Entitlement    套餐、用量、额度、发票、试用、超额和功能开关
Operations               告警、审计、备份、灾备、SLO、事故和变更管理
Marketplace              检查器、适配器、规则包、企业内部插件
```

每个领域应有自己的应用服务、数据表、事件和权限检查，跨领域访问通过明确的接口或事件完成。不能让前端知道 MySQL 表名，也不能让 Worker 直接修改租户账单对象。

### 3.2 推荐服务边界

第一阶段仍然可以是模块化单体加独立 Worker，不应为了“微服务”提前拆成十几个部署单元。建议边界如下：

- `control-plane`：Spring Boot。身份、租户、成员、组织设置、仓库连接、策略、计费、审计、Webhook 接收和外部集成编排。
- `agent-runtime`：Python FastAPI/Worker。验证图、Contract 编译、LLM Provider、RAG、沙箱执行、评测和证据生成。
- `evidence-service`：早期可以是 Python 模块，后续在大客户场景拆出。负责证据对象、摘要、签名、证书验证、Capsule 重放索引。
- `web`：React/TypeScript。只通过版本化 API 与 SSE/WebSocket 访问后端。
- `scheduler`：负责任务优先级、租户公平、并发额度、延迟队列和周期评测；早期可以复用 Worker 进程，规模上来后单独部署。
- `connector-workers`：GitHub、GitLab、Jira、Slack、企业微信、飞书等外部连接器，采用统一 Connector SPI。

控制面和运行时不应共享全部领域模型。共享的只有事件 Envelope、租户 ID、Job ID、Trace ID、版本化 API Schema 和签名验证库。

### 3.3 数据分层

建议采用以下持久化分层：

- PostgreSQL 或 MySQL：租户、用户、角色、仓库、Specification、Contract、Job、状态转移、Finding 索引、账单用量和审计事实。
- MongoDB 或 PostgreSQL JSONB：LangGraph checkpoint、动态评测工件、模型响应元数据、实验参数和复杂差异结果。重要结论索引仍回写关系库。
- Redis：租约、幂等键、速率限制、短期预算、SSE/Stream、分布式锁。所有非事实数据必须 TTL 或可重建。
- RabbitMQ 或 Kafka：可靠命令、任务事件、审计事件和集成事件。任务执行至少一次，业务处理幂等。
- MinIO/S3：报告、Capsule、补丁、日志片段、签名证书、回放包。对象名不可直接由用户输入拼接，必须带租户隔离和 digest。
- Elasticsearch/OpenSearch：仓库符号、需求、Contract、Finding 和证据全文检索。搜索结果不能直接决定判定等级。
- ClickHouse 或可查询指标仓：长期用量、性能、成本和组织级分析，可在商业版再引入。

### 3.4 事件 Envelope

所有跨服务事件必须使用统一 Envelope，最少包含：

```json
{
  "event_id": "ulid",
  "event_type": "verification.job.created.v1",
  "occurred_at": "2026-08-18T00:00:00Z",
  "tenant_id": "tenant_123",
  "actor_id": "user_456",
  "trace_id": "trace_789",
  "aggregate_type": "verification_job",
  "aggregate_id": "job_abc",
  "schema_version": 1,
  "idempotency_key": "github:delivery:...",
  "payload": {},
  "payload_digest": "sha256:..."
}
```

事件消费者必须记录 inbox 或处理标记，失败要区分可重试、人工处理和永久拒绝。事件内容不能携带明文 API Key、私钥、完整源代码和未脱敏模型请求。

## 4. 后端完整建设指南

### 4.1 身份、租户和权限

API Key 只能作为早期内部接入方式。商业版必须建立统一身份模型：User、Organization、Tenant、Membership、Role、Permission、ServiceAccount、ApiToken、SsoConnection、ScimDirectory、Session 和 Device。一个用户可以加入多个组织，一个组织可以有多个仓库和环境，一个服务账号只应拥有必要的机器权限。

建议角色至少包括：Owner、Admin、Security Reviewer、Release Manager、Developer、Auditor、Billing Manager、Read Only。权限不要只写成页面权限，要落到资源和动作，例如 `job:read`、`job:cancel`、`contract:approve`、`finding:waive`、`certificate:issue`、`repository:connect`、`policy:publish`、`billing:read`。

所有资源查询都必须带 tenant scope。不能先查全局列表再在 Python 内存中过滤，因为错误日志、分页总数和时间窗口都可能泄露跨租户信息。数据库层增加 tenant_id 复合索引，关键表用行级权限或 Repository 层强制注入租户条件。

### 4.2 Job 状态机

生产状态机建议固定并版本化：

```text
CREATED -> QUEUED -> DISPATCHED -> RUNNING
RUNNING -> WAITING_FOR_PROVIDER -> RUNNING
RUNNING -> SUCCEEDED / BLOCKED / FAILED / CANCELLED / STALE
QUEUED -> CANCELLED / FAILED
WAITING_FOR_PROVIDER -> RUNNING / FAILED / CANCELLED
```

每次迁移必须执行 CAS，记录 `from_status`、`to_status`、`actor_type`、`reason`、`trace_id`、`created_at`。不允许通过直接 UPDATE 绕过状态机。客户端只显示业务状态和当前阶段，不把内部异常堆栈直接暴露给普通成员。

取消不是简单设置一个布尔值。API 先写取消请求和状态 CAS，Worker 在每个长阶段边界、Maven 执行前后、LLM 重试前和消息确认前检查取消标记；无法立即终止的沙箱进程必须有最大等待时间，最终由回收器处理。

### 4.3 提交验证 API

推荐使用 `/api/v1` 版本化 API。最小资源包括：

```text
POST   /api/v1/organizations
GET    /api/v1/organizations/{id}
POST   /api/v1/repositories
POST   /api/v1/repositories/{id}/connections/test
POST   /api/v1/specifications
POST   /api/v1/specifications/{id}/compile
POST   /api/v1/contracts/{id}/approve
POST   /api/v1/verifications
GET    /api/v1/verifications
GET    /api/v1/verifications/{id}
POST   /api/v1/verifications/{id}/cancel
GET    /api/v1/verifications/{id}/stages
GET    /api/v1/verifications/{id}/matrix
GET    /api/v1/verifications/{id}/findings
GET    /api/v1/verifications/{id}/evidence
POST   /api/v1/verifications/{id}/replay
POST   /api/v1/findings/{id}/waive
POST   /api/v1/findings/{id}/fix-proposal
POST   /api/v1/certificates/{id}/verify
GET    /api/v1/audit-events
GET    /api/v1/usage
```

创建验证任务必须支持 Idempotency-Key。请求体应引用 Repository、Base SHA、Head SHA 和 Specification 版本，服务端重新解析并校验路径、Commit 所属仓库、权限、配额和策略。不能让客户端提交任意宿主机路径。早期 CLI 的 `--repo` 仍可以保留，但 SaaS API 只接受已连接仓库或受控上传对象。

### 4.4 Contract 领域增强

Contract 应从简单 JSON 记录升级成可追踪实体：

- `contract_id`：稳定 ID，不因文字微调而随意变化。
- `specification_id` 与 `spec_version`：指向需求版本。
- `family`：AUTH、UNIQUE、TRANSACTION、EVENT_ONCE、MIGRATION、OPENAPI、CONSTITUTION 等。
- `priority` 与 `risk_level`：区分业务重要性和技术风险。
- `preconditions`、`stimulus`、`expected_observation`、`forbidden_observation`：让契约可执行。
- `approval_state`、`approved_by`、`approved_at`、`review_comment`：人工治理。
- `checker_versions`：记录使用了哪个检查器版本。
- `lineage`：从需求句子到 Contract、测试、证据和证书的 DAG。

引入 Contract 变更时，不要覆盖旧版本。对于高风险领域，修改 Contract 后必须重新审批，旧证书不能自动继承。前端要能显示“原文需求、编译解释、人工改写、执行方式和历史版本”的对照视图。

### 4.5 执行沙箱

沙箱是上线阻断项，不是优化项。执行任意 PR 代码时至少保证：非 root 用户、无网络、丢弃 Linux capabilities、no-new-privileges、CPU/内存/PID/磁盘限制、只读源代码、仅允许 target 或临时目录写入、不注入宿主机密钥、不挂载 docker.sock、超时强杀、输出长度限制、工作目录自动回收。

执行器做成插件接口：

```python
class ExecutionAdapter(Protocol):
    def detect(self, repo: RepositorySnapshot) -> RuntimeProfile: ...
    def prepare(self, request: ExecutionRequest) -> PreparedExecution: ...
    def run(self, prepared: PreparedExecution) -> ExecutionResult: ...
    def collect(self, prepared: PreparedExecution) -> EvidenceFragment: ...
    def cleanup(self, prepared: PreparedExecution) -> None: ...
```

第一批适配器是 Java/Maven、Java/Gradle、Node、Python、Go。每个适配器必须声明镜像 digest、工具链版本、可离线缓存策略和已知限制。不要把“支持任意项目”写进营销页面；应按已验证的语言、框架和构建系统展示兼容矩阵。

### 4.6 LLM Provider 治理

Provider 层需要从“能调用模型”升级为“可运营模型供应链”：模型注册、能力探测、区域、数据保留、最大上下文、结构化输出、流式、工具调用、价格、速率、熔断、重试、预算、缓存和审计。

推荐路由策略：

1. 需求解析和简单摘要优先使用低成本模型。
2. Contract 编译和审查法庭使用可解释、结构化输出稳定的模型。
3. 生成测试和复杂诊断允许使用高推理模型，但必须有 token 与时间预算。
4. 每次 LLM 调用记录 `provider_id`、`model_id`、`prompt_digest`、输入/输出 token、缓存命中、延迟、重试和降级原因；记录摘要，不默认保存完整私有代码。
5. JSON 校验失败时只允许有限修复重试，仍失败则走确定性模板，结果标记为 deterministic fallback。

所有仓库内容都当作数据，不当作系统指令。Prompt 结构使用明确的 `SYSTEM_POLICY`、`UNTRUSTED_REPOSITORY_DATA`、`TASK_INPUT` 和 `OUTPUT_SCHEMA` 分段；模型生成的工具调用必须经过服务器端白名单、租户权限和参数校验，不能把模型返回的路径直接交给 shell。

### 4.7 证据、签名和重放

证据对象必须有稳定的内容摘要和来源链：

```text
Specification digest
    + Contract digest
    + Base SHA / Head SHA
    + Checker version
    + Runtime image digest
    + Test command and exit code
    + Observation digest
    -> Evidence digest
    -> Capsule manifest digest
    -> Signed certificate statement
```

SHA-256 是完整性摘要，不要把它误称为签名。签名采用 Ed25519 或企业 KMS/HSM，证书应包含 issuer、subject、predicate、validity、key id、algorithm、revocation endpoint 和 lineage extension。密钥轮换后旧证书仍可离线验证；密钥撤销不能删除历史证据，而应改变验证状态。

Capsule 需要支持 Linux 和 Windows 两种回放入口，包含 manifest、需求、Contract、最小化 fixture、生成测试、环境说明、run.sh、run.ps1 和预期结果比较器。Capsule 不应打包完整仓库和敏感密钥，默认只打包最小必要证据，并在生成和下载前做二次秘密扫描。

## 5. 前端完整建设指南

### 5.1 信息架构

商业版前端建议从当前侧栏扩展为按角色可见的工作台：

```text
工作台
  总览 / 我的待办 / 失败趋势 / 配额状态 / 最近证书
验证中心
  新建验证 / 任务列表 / 任务详情 / 阶段时间线 / 需求矩阵
证据中心
  Findings / Capsule / Certificate / Replay / 证据检索
治理中心
  Specification / Contract / 策略 / 审批队列 / 宪法规则
代码与集成
  仓库 / GitHub App / GitLab / CI Token / Webhook / Check Runs
组织管理
  成员 / 角色 / SSO / Service Account / API Token / 审计日志
运营与计费
  用量 / 配额 / 套餐 / 发票 / 成本分析 / 告警
系统设置
  Provider / 沙箱 / 保留策略 / 通知 / 区域 / 数据导出
```

不同角色不应看到相同的首页。Developer 关注自己的任务和修复建议；Reviewer 关注待审批 Contract 和 Finding；Security 关注高风险、豁免和证书；Admin 关注成员、集成、配额和健康；Auditor 关注只读证据和审计时间线。

### 5.2 新建验证向导

新建验证不能只让用户填写五个路径输入框。推荐四步向导：

1. 选择仓库与 PR：从已连接平台选择 repository、pull request、Base/Head SHA，服务端展示分支和提交作者。
2. 选择需求：上传需求、选择 Specification 版本或从 Issue/PR 描述导入，自动显示解析出的 Contract 候选。
3. 选择档位：FAST、DEEP、RELEASE，自定义并发、超时、是否启用变异、是否发布 Check Run。
4. 复核与提交：展示预计用量、数据处理区域、敏感信息扫描结果、待审批 Contract 和风险提示，提交后进入实时状态页。

### 5.3 任务详情页

任务详情是最关键页面，建议采用顶部摘要、中心时间线、底部证据三栏布局：

- 顶部：Job 状态、仓库、PR、Base/Head、档位、耗时、操作者、终态原因和取消/重试按钮。
- 时间线：每个节点的状态、耗时、输入摘要、输出摘要、重试次数、降级信息和 trace 链接。
- 需求矩阵：每条 Contract 的结果、证据引用、checker 版本、置信度和是否经过人工审批。
- Finding：严重度、是否阻断、归因、位置、实际观察值、预期值、反例测试和 Capsule。
- 证书区：签名状态、公钥 ID、摘要、验证结果、下载和离线验证命令。
- 失败诊断：区分需求歧义、仓库不可访问、构建失败、Provider 不可用、沙箱限制、真实回归和证据不足。

### 5.4 设计系统

工业控制台应该强调可扫描、可比较和可追责，而不是营销页面式大卡片。保留当前深色工业风可以，但需要补齐设计令牌：颜色语义、间距、字号、焦点环、状态色、危险操作、禁用态、加载态、空态和错误态。卡片圆角不超过 8px，表格支持固定列、列显隐、筛选、排序、复制和导出。

状态颜色不能只依赖红绿：用颜色加文字和图标表达 `PASS`、`FAIL`、`BLOCKED`、`UNVERIFIED`、`DEGRADED`、`WAITING`。所有按钮都要有键盘焦点和明确禁用原因。详情页的大段日志要支持折叠、搜索、复制和下载，不能把完整日志一次性塞入 DOM。

### 5.5 实时性与弱网

SSE 继续适合阶段进度，但商业版要加入 Last-Event-ID、心跳、指数退避、断线后增量补齐和最终状态回查。前端状态模型不要把 SSE 当作唯一事实源；收到事件后更新临时状态，任务完成或重新连接时从 REST 重新拉取。对超过 30 秒的重连显示“正在恢复进度”，而不是无限转圈。

### 5.6 前端质量

新增 Vitest/Testing Library 覆盖路由守卫、鉴权过期、SSE 重连、降级态、跨租户不可见、危险操作二次确认、Capsule 下载、证书验证、表格筛选和移动端布局。Playwright 覆盖新建验证、任务详情、Finding、审批、登录、权限拒绝和错误恢复。前端构建门禁必须包括 TypeScript、lint、单测、生产构建、关键页面截图回归和无障碍扫描。

## 6. 可以新增的复杂能力

### 6.1 证据图谱与需求血缘

把需求、Contract、代码符号、测试、数据库观察、Finding、Capsule、Certificate、Fix PR 和审批连接为图。用户可以从一句需求点到对应的代码路径，也可以从一个 Finding 反查哪些证书、哪些租户和哪些发布受它影响。图谱还可以发现“需求没有任何执行证据”“一个高风险 API 没有 Contract”“一个 Contract 被多次跳过”等治理问题。

### 6.2 自适应验证编排

根据 diff 风险、变更文件、历史失败、仓库类型和租户策略自动决定 FAST/DEEP/RELEASE 的检查组合。例如只改注释时快速验证；修改权限注解、数据库迁移和消息消费时自动升级；连续出现同一回归时增加变异战役和全栈状态差分。升级原因必须可解释，用户可以允许或拒绝自动升级。

### 6.3 反例生成与最小化

当前生成测试后要继续做反例最小化：删除无关步骤、缩短输入、压缩 fixture、缩小时间窗口、保留导致差异的最小请求序列。这样 Finding 更容易被开发者理解，也能降低 Capsule 体积和回放成本。最小化过程本身要记录尝试次数和未改变结论的证明。

### 6.4 状态机和并发验证

增加基于模型的状态机测试、时钟扰动、消息重复、乱序、延迟注入、Redis 丢失、数据库死锁和重试风暴。对支付、库存、权限、订单、Webhook 等领域，验证“最终状态”还不够，必须验证不可违反的不变量，例如余额不为负、同一幂等键最多产生一个业务副作用、已撤销 Token 不能恢复访问、事务失败不能留下半提交状态。

### 6.5 AI 生成修复闭环

Finding 产生 Fix Proposal，但 Fix Proposal 永远不能直接合并。流程应为：证据确认 -> 生成最小补丁 -> 静态与测试自检 -> 人工批准 -> 创建分支/PR -> 新 Head 再验收 -> 比较修复前后证据。修复服务必须限制文件范围、命令白名单和修改预算，并能够回滚到原始 Head。前端显示每一步的责任人和审批状态。

### 6.6 组织级策略即代码

提供 Policy DSL 或 YAML：哪些目录禁止改动、哪些 Contract 必须人工批准、哪些 severity 需要 Security Reviewer、哪些仓库不允许外部 LLM、哪些证书必须 HSM 签名、哪些任务不得访问网络、哪些 Findings 可以豁免以及豁免有效期。策略发布有版本、审批、生效时间和回滚。策略判断要成为证据的一部分。

### 6.7 多模型评审法庭

在高风险任务中允许 Prosecutor、Defender、Judge 使用不同 Provider 或不同模型，避免单模型自洽。增加反事实问题：“如果 Base 和 Head 都失败，是否仍能归因于 Head？”“如果测试偶然通过，哪条证据仍然成立？”“是否存在一个更小的反例？”最终裁决仍由硬政策和真实实验约束，模型只是提出主张和反证。

### 6.8 私有化模型与数据域

企业版支持本地 vLLM、DeepSeek、Qwen、Azure OpenAI、OpenAI-compatible Gateway，按租户或仓库选择 Provider。数据域配置包括代码是否允许出域、prompt 是否留存、日志是否脱敏、embedding 是否本地化、证据保存区域和删除周期。模型不可用时任务要进入 WAITING_FOR_PROVIDER 或确定性降级，不应伪造通过。

### 6.9 研发效能和质量分析

在不泄露代码的前提下统计：按仓库/团队/语言/Contract 家族的回归率、误报率、未验证率、平均修复时间、重放成功率、沙箱失败率、模型成本、缓存命中、证书覆盖率和豁免到期率。不要把“发现越多问题”简单当作团队质量变差，分析页面必须区分变更量、风险结构和检测覆盖率。

### 6.10 插件市场

建立 Checker、Execution Adapter、Policy Pack、Notification Connector、Evidence Exporter 的统一插件协议。每个插件有 manifest、版本、权限声明、输入输出 Schema、签名、兼容矩阵、资源上限和安全扫描报告。插件默认无权访问网络和宿主机，企业管理员显式批准后才能启用。

用量不要只保存在 Redis。每次任务完成后写不可变账本：租户、任务、档位、执行秒数、沙箱资源、输入 token、输出 token、缓存命中、存储字节、外部连接调用次数、模型成本估算、计费单位、调整原因。账本允许追加冲正，不允许直接修改历史行。账单汇总可以异步计算，但必须能够从账本重建。

## 8. API、MCP 与外部集成

### 8.1 API 兼容策略

所有响应带 `request_id`、`schema_version` 和必要的 `degraded` 信息。错误使用稳定编码，例如 `AUTH_REQUIRED`、`TENANT_FORBIDDEN`、`QUOTA_EXCEEDED`、`JOB_NOT_FOUND`、`PROVIDER_UNAVAILABLE`、`EVIDENCE_UNVERIFIED`。不要让前端依赖英文异常字符串或 Python 堆栈。

破坏性变更使用 `/v2` 或媒体类型版本；新增字段保持向后兼容；删除字段至少经过一个弃用周期。OpenAPI 生成后要做 schema diff，CI 阻止未记录的破坏性变更。

### 8.2 MCP 产品化

当前 MCP 服务端可以继续保持精简，建议稳定提供六类核心工具：`verify`、`get_job`、`get_matrix`、`get_findings`、`replay_info`、`health`。不要为了“工具多”把内部数据库和任意 shell 暴露给外部 Agent。每个工具都要经过身份、租户、速率、参数大小和数据脱敏检查，错误通过 `isError` 和稳定错误码返回。长任务工具返回 job_id，外部 Agent 用查询工具轮询，不阻塞 MCP 连接。

后续可以增加受控的 MCP 客户端，让 SpecCraft 调用外部测试、Issue 和文档工具，但必须有工具注册表、能力声明、批准策略、调用预算、结果大小上限和不可信结果隔离。外部工具的输出只能作为数据，不能覆盖系统策略。

### 8.3 GitHub/GitLab 集成

Webhook 接收先验签、限速、去重和快速返回，再通过 Outbox 建立任务。Check Run 只写摘要和链接，详细证据放在控制台或对象存储。重复 delivery 必须幂等。权限不足、网络失败和仓库删除都进入可诊断状态，不能把集成失败误写成验证通过。

## 9. 测试与评测体系

### 9.1 测试金字塔

目标不是追求一个漂亮的测试数量，而是让每类故障都有对应测试：

- 单元：解析器、状态机、证据政策、鉴权、租约、幂等、脱敏、签名、路径安全、前端组件。
- 合同测试：服务间事件、OpenAPI、MCP JSON-RPC、GitHub Webhook、Check Run payload。
- 集成：真实 MySQL、Redis、RabbitMQ、MongoDB、MinIO、Elasticsearch 的关键路径。
- 端到端：提交 PR -> 建 Job -> Worker -> 报告 -> Check Run -> 证书。
- 故障注入：API 崩溃、Outbox 重复、MQ 重投、Worker 中断、Provider 429/500/超时、Redis 丢失、数据库故障、对象存储半成功、时钟回拨、磁盘满。
- 安全：越权、跨租户读取、路径穿越、Webhook 验签、Prompt 注入、秘密泄漏、沙箱逃逸、恶意构建脚本。
- 评测：正样本、负样本、holdout、对抗样本、跨框架样本和重复运行漂移。

### 9.2 金案例和 Go/No-Go

继续扩展到 200 个金案例，至少覆盖权限、Token、唯一性、事务、并发、消息重复、迁移、缓存一致性、OpenAPI、配置、日志泄漏、依赖升级和注入。每个案例有 spec、base、head、期望 Contract、期望 severity、期望 evidence_type、是否应阻断、最小回放命令和人工解释。

holdout 案例必须在开发阶段隔离，评测报告记录案例集版本、模型版本、Provider、prompt digest、运行环境和结果摘要。目标指标建议为：高风险召回率至少 99%、负样本误报为 0、证据重放成功率至少 99%、连续 20 次运行无结论漂移、取消任务无幽灵执行、任务丢失率为 0。

### 9.3 发布门禁

每个版本必须通过：前端 build、ruff、mypy、bandit、unit、合同测试、关键 integration、金案例 smoke、秘密扫描、OpenAPI diff、迁移前向测试、迁移回滚测试、Capsule 验证和变更记录检查。全量 Docker/Compose 和 Windows 打包属于明确的发布验收任务，不能在普通开发迭代中每次重复执行。

## 10. 安全、合规和隐私

### 10.1 威胁模型

攻击者可能提交恶意仓库、恶意 pom/npm 脚本、Prompt 注入文本、伪造 Webhook、重放请求、猜测 Job ID、制造大文件/大输出/高并发、窃取 Provider Key、利用跨租户查询、伪造证书或通过插件访问宿主机。每个威胁必须对应代码控制、测试和监控告警。

### 10.2 密钥管理

开发环境使用 `.env.example` 占位符；生产用 Docker Secret、Vault、云 KMS 或企业密钥系统。API Key、GitHub 私钥、LLM Key、签名私钥不进源代码、不进日志、不进 Capsule、不进聊天。日志脱敏必须覆盖异常堆栈、请求头、查询字符串、模型 payload、子进程环境和生成的报告。

### 10.3 合规路线

商业化早期先完成数据清单、处理目的、保存期限、删除流程、访问审批、备份加密和事故响应。之后根据目标市场推进 SOC 2、ISO 27001、等保或客户专属审计。不要在没有证据和制度的情况下在网页上宣称“符合某标准”；应把控制项、责任人、证据和审计周期写成内部控制矩阵。

## 11. 可观测性与运维

### 11.1 SLO 建议

初版可以使用：API 可用性 99.9%；Webhook 接收 p95 小于 1 秒；FAST 小 PR p95 小于 8 分钟；DEEP 小 PR p95 小于 25 分钟；任务丢失率 0；证据摘要冲突率 0；租约恢复成功率 99.9%；高等级 Finding 证据完整率 100%。SLO 必须按租户、档位和仓库类型分层，不能用所有任务平均值掩盖长尾。

### 11.2 指标

应用指标：HTTP 请求数、错误数、延迟、认证失败、限流、任务状态、阶段耗时、队列深度、Outbox 积压、租约续期、重试、取消、Provider 错误、模型 token、缓存命中、沙箱 CPU/内存/磁盘、证据生成失败、Capsule 重放成功率、Check Run 失败和账单用量。

日志字段：`timestamp`、`level`、`service`、`environment`、`tenant_id`、`actor_id`、`job_id`、`stage`、`trace_id`、`request_id`、`event_id`、`error_code`、`duration_ms`、`degraded`。日志必须结构化输出，敏感字段在序列化前清理。

### 11.3 备份与灾备

MySQL 每日全量、增量或 binlog；对象存储开启版本和跨区域/冷存储策略；Mongo checkpoint 按保留期备份；Redis 只备份需要恢复的限流/调度配置，不把它当业务事实源。每季度做恢复演练，测量 RPO/RTO，而不是只检查备份文件存在。

### 11.4 事故流程

事故分为安全、数据、可用性、正确性和计费五类。正确性事故优先级不低于可用性事故，因为错误地签发证书可能造成真实合并风险。事故处置要能暂停新任务、冻结证书签发、撤销集成、隔离 Provider、停止有风险的执行器、保留证据和通知客户。事后必须有时间线、影响范围、根因、修复、回归测试和是否需要撤销证书。

## 12. 分阶段开发计划

以下计划按“可独立验收的阶段”组织，不要求每周构建安装包或 Docker 镜像。部署线只在阶段出口和发布候选时执行。

### 阶段 0：基线冻结与架构治理，1-2 周

目标：把当前能力变成可维护基线。

任务：

- 固定当前 Python、Node、JDK、Maven、依赖锁定和数据库迁移版本。
- 生成代码地图、API/OpenAPI 基线、事件清单、数据字典和依赖许可证清单。
- 将现有未提交改动逐项标注为用户工作、实验工作或正式功能，不做无授权清理。
- 修复弃用警告、补充启动配置检查、统一错误码和 Request-ID。
- 为现有 627 个 unit 测试建立基线报告，区分本地通过、集成跳过和外部依赖未验证。

出口：新机器可以按 README 启动 CLI 和前端；CI 能执行静态检查和 unit；所有已有能力有责任边界和文档链接。

### 阶段 1：商业身份与多租户，3-5 周

任务：

- Spring Control Plane 完成 User、Organization、Membership、Role、Permission、Service Account。
- 接入 OIDC，随后实现 SAML；加入短期 Access Token、Refresh Token、API Token 轮换和撤销。
- 所有 Python API 增加 tenant scope、资源授权和审计字段。
- 增加组织切换、成员邀请、角色编辑、Token 管理和登录失败告警。
- 建立租户级配额和默认数据保留策略。

出口：两个租户之间无法读取任何 Job、Contract、Evidence、用量和审计；权限矩阵自动化测试全绿。

### 阶段 2：完整验证工作流与前端，4-6 周

任务：

- 新建验证向导、仓库选择、Specification 版本选择、档位与预算预览。
- 任务详情的阶段时间线、矩阵、Finding、Certificate、Capsule 和 Replay 页面。
- SSE 断线续传、REST 回查、错误边界和移动端布局。
- 增加任务过滤、批量取消、重试、收藏、标签和通知中心。
- API 统一分页、排序、筛选、错误码和 OpenAPI Schema。

出口：开发者不使用 CLI 也能完成一次验证、理解阻断原因、下载 Capsule 并验证证书。

### 阶段 3：仓库集成与策略中心，4-6 周

任务：

- GitHub App 的安装、仓库选择、Webhook、Check Run、评论和重试管理。
- GitLab、Gerrit 和通用 CI Webhook 适配器。
- Policy DSL、宪法规则、Contract 审批流、Finding 豁免流。
- 分支保护建议、必须通过的 Contract 家族、指定 Reviewer 和发布窗口。
- 证据链中写入策略版本和审批记录。

出口：客户从 PR 页面触发验证，结果自动回写；策略可以阻止未批准 Contract 或证据不足的合并。

### 阶段 4：验证深度与执行生态，6-8 周

任务：

- Java/Gradle、Node、Python、Go 执行适配器。
- 状态机模型测试、并发与消息乱序、迁移安全、缓存一致性和变异战役增强。
- 反例最小化、跨运行重放、失败聚类和相似 Finding 去重。
- 沙箱镜像版本清单、离线缓存管理、资源配额和回收器。
- 增加 100 个以上高质量金案例和 holdout 隔离。

出口：兼容矩阵、性能基准、故障注入和安全测试达到发布门槛；不支持的仓库类型能清晰拒绝。

### 阶段 5：证书、合规与私有化，4-6 周

任务：

- KMS/HSM 签名适配器、密钥轮换、证书撤销和离线验证。
- 对象加密、租户级区域、数据删除、导出、审计查询和保留策略。
- 私有 Provider、内网镜像仓库、私有 MinIO/S3、LDAP/SCIM。
- 生成部署前置检查、备份恢复演练和升级/回滚手册。

出口：至少一个模拟企业环境完成从安装、导入、执行、备份、恢复到升级回滚的全流程。

### 阶段 6：计费、用量和商业运营，3-5 周

任务：

- Plan、Subscription、Entitlement、Usage Ledger、Invoice 和优惠码模型。
- 任务点数/执行分钟/仓库数/并发额度的计量和超额策略。
- 管理员用量看板、预算告警、冻结策略、账单导出和客服查询工具。
- 试用、升级、降级、欠费宽限、取消和数据保留流程。

出口：财务可以从不可变用量账本重建账单；客户能看到额度和消耗原因；计费异常不会影响证据正确性。

### 阶段 7：SpecCraft 生产闭环，6-8 周

任务：

- 规划、诊断、编辑、命令、测试、记忆、流式、预算和 checkpoint 统一成 Agent Job。
- 接入仓库 `AGENTS.md`、`CLAUDE.md` 和组织策略，但所有规则有优先级和来源。
- 增加受控并行子任务、工具白名单、变更预览、人工批准和撤销。
- Craft 完成后强制交给 SpecProof 独立验证，不能自签证书。
- 建立 SpecCraft 10 任务微基准和陷阱变体自校验拦截率。

出口：Agent 可以完成受控任务，失败时可续跑、可解释、可回滚；所有修改有 Diff、测试和独立验收证据。

### 阶段 8：平台化和生态，持续迭代

任务：插件市场、IDE 扩展、MCP 客户端、Jira/飞书/Slack 通知、跨仓库趋势、证据图谱、行业规则包、模型路由优化和多区域高可用。

出口：外部开发者可以在权限隔离下开发适配器；平台每季度用公开和私有基准重新评估，不靠一次性演示维持产品叙事。

## 13. 团队配置和研发方法

最小可行商业团队建议 8-12 人：产品负责人 1、技术负责人 1、后端/控制面 2、Python Agent/执行器 2、前端 2、平台/SRE 1、安全与测试 1，可兼职设计和客户成功。不要让一个人同时负责沙箱安全、计费、前端和客户交付，这些领域的失败模式不同。

研发采用“先写验收再实现”：每项能力先写数据契约、权限矩阵、异常路径、指标和测试；再实现一个纵向切片；最后补集成和文档。每两周做一次演示，但演示只允许使用真实产生的证据。每月做一次安全和成本审计，每季度重跑金案例、灾备和兼容矩阵。

代码评审重点不是行数，而是：是否绕过状态机、是否丢失 tenant scope、是否把不可信文本当指令、是否直接使用用户路径、是否把静态证据升级为 BLOCKER、是否把 Redis 当事实源、是否让任务在重试后重复副作用、是否留下未审计的外部调用、是否新增了无法清理的对象和日志。

## 14. 当前仓库建议的首批落地任务

下面是最值得立刻执行的 15 个任务，顺序经过风险和收益排序：

1. 建立 `docs/architecture/domain-model.md`，冻结当前领域对象和未来租户对象。
2. 给 FastAPI 和 Spring Control Plane 统一 `request_id`、`trace_id`、错误码和审计 Envelope。
3. 为每个 API route 补 tenant scope 设计，即使早期只有一个默认租户，也不要继续扩散全局查询。
4. 增加 OpenAPI schema diff 门禁和事件 Envelope 合同测试。
5. 将前端新建验证向导、任务详情、权限拒绝和降级态列为第一批 Playwright 场景。
6. 为 Contract 增加 immutable version、approval、checker version 和 lineage 字段。
7. 把证书验证、Capsule 下载和 Replay 从文件路径推断改为对象元数据查询。
8. 为 Worker 增加取消检查、租约指标、阶段耗时和统一异常分类。
9. 为 Provider 增加每租户预算、模型路由、调用摘要和成本账本。
10. 建立 Java/Maven、Node、Python、Go 的执行适配器接口和兼容矩阵，不立即实现所有适配器。
11. 增加跨租户、路径穿越、Webhook 重放、Prompt 注入和沙箱边界安全测试。
12. 把当前金案例扩展计划拆成可审阅的案例表，每个案例先写 expected evidence 再写实现。
13. 处理 `httpx`/Starlette TestClient 弃用警告，避免升级依赖时突然变成阻断错误。
14. 为数据保留、删除、导出和备份恢复写成操作手册，并做一次不依赖 Docker 的文档演练。
15. 在代码和文档中继续区分“已实现”“本地验证”“需要真实基础设施”“规划中”，这是项目可信度的一部分。

## 15. 发布验收清单

### 15.1 代码和构建

- Python 依赖锁定、ruff、mypy、bandit 通过。
- 前端 TypeScript、lint、unit、生产 build 通过。
- Spring Control Plane 测试和依赖扫描通过。
- 数据库迁移可从空库前向执行，兼容升级可回滚或有明确不可逆说明。
- OpenAPI、事件和 MCP Schema 没有未审阅的破坏性变更。

### 15.2 功能和证据

- 需求可解析为 Contract，Contract 可审批、拒绝、撤销和版本追踪。
- Job 能创建、排队、运行、取消、失败、等待 Provider、恢复和结束。
- 每个 Finding 能反查需求、代码差分、测试、执行结果、环境和 Capsule。
- 没有真实证据的结论显示 UNVERIFIED，而不是 PASS。
- Capsule 在独立环境可重放，证据摘要和证书签名可验证。

### 15.3 安全和治理

- 未配置生产密钥时 fail-closed。
- 租户隔离、权限、Webhook 验签、API 限流、路径校验和秘密脱敏有自动化测试。
- 执行不可信 PR 时无 root、无网络、无宿主机密钥和 docker.sock。
- 审计记录覆盖登录、成员、策略、Contract、Job、Finding 豁免、证书和导出。
- 数据删除、备份恢复、密钥轮换和事故暂停有可执行手册。

### 15.4 运营和商业

- 每个套餐的功能、并发、存储、保留期和支持范围可解释。
- 用量账本可重建，预算超限有明确状态和通知。
- Dashboard 显示降级和数据不可用原因，不用空值伪造成本和指标。
- 监控覆盖队列、Outbox、Worker、Provider、沙箱、对象存储、数据库和证书。
- 至少完成一次发布前恢复演练和一次安全响应演练。

## 16. 结语：什么才叫“完整的大项目”

完整大项目不是前端页面数量多、后端服务数量多或 Docker Compose 文件很长。对 SpecProof 来说，真正的完整性是：研发人员可以自然地提交变更，系统可以在可控时间内完成验证，结论对需求负责，证据对结论负责，证书对证据负责，权限和租户对数据负责，账单对用量负责，运维对故障负责，开发计划对现实负责。

项目现在已经拥有一条非常有价值的技术主线：独立验证、契约编译、差分实验、沙箱执行、证据胶囊、签名证书和 Agent 闭环。下一步不应继续无边界增加“看起来先进”的模块，而应沿着多租户治理、完整工作流、执行器生态、数据和证据生命周期、商业计费、企业身份、可靠运维和可验证评测逐步收口。每增加一个复杂能力，都要同时增加权限、数据模型、错误路径、指标、测试、文档和回滚方案。

按照本文计划推进，最终产品应形成两个互相制约但互相增益的系统：SpecCraft 负责提高实现速度，SpecProof 负责提供独立可信的验收。写代码的 Agent 永远不能给自己签字；平台的价值就建立在这条边界之上。
