## 一、先给结论

### 1.1 项目真正要解决的问题

SpecProof 解决的不是“让大模型再看一次 Diff”，而是解决 AI 生成代码进入团队协作后
“谁负责验收、怎样证明需求真的完成、怎样证明严重问题不是误报、怎样在另一台机器
重放同一事实”这四个问题。项目把需求、验收标准、禁止变更、Base 提交、Head 提交、
执行环境和工具链组合成一条可审计链路，再把每条需求映射成可执行 Contract。只有
Contract 有真实执行结果、严重 Finding 有可复现证据、证据和提交及需求摘要能够对应时，
系统才允许生成通过性结论；如果数据不完整，结果必须显示 `UNVERIFIED`、`NEEDS REVIEW`
或 `FAILED`，不能用默认值填成 PASS。

SpecCraft 是同一平台的另一半。它负责规划、检索、编辑、执行、自校验、交付，目标是
提高实现速度；SpecProof 负责独立验收，目标是阻止实现 Agent 给自己签字。两者可以共享
工具、状态、预算和 UI，但必须在信任边界上分离：SpecCraft 生成的自评只能作为输入，
不能作为 Merge Certificate 的签发依据。

### 1.2 当前真实定位

`specproof-phase0` 是七天原型，重点验证单个 Spring Boot 仓库的 Base/Head 差分和
Bug Capsule；`specproof-dbg-c18` 是经过内核加固的验证主线样本，加入了合同结果合并、
H2 文件数据库取证、Review Court 证据政策、可靠性内核和真实 Worker；
`specproof-clean-clone-gate` 是目前最完整的演进主线，已经扩展到 Web 控制台、租户身份、
SpecCraft、MCP、RAG、GitHub 集成、用量账本、沙箱、执行适配器和更大评测集。

但是，`D:\experim` 根目录是无提交的实验汇总目录，里面还保留大量旧副本、回滚草稿、
基准工作目录、备份 bundle 和临时报告。它适合作为研究工作区，不适合作为产品交付根目录。
后续的第一项治理工作不是继续加模块，而是把 `specproof-clean-clone-gate` 明确成唯一
可发布主线，把其他副本标注为历史基线、实验分支、评测夹具或冻结草稿，并在仓库外保留
原始备份，避免“复制文件即合并”的不可追溯演进方式。

### 1.3 当前能力的可信分层

当前主线已经有一条较完整的纵向链路：CLI/FastAPI/MCP 入口，需求解析，契约编译，
Base/Head 隔离，静态检查，Counterexample 测试生成，Maven 执行，差分结果，Review Court，
矩阵，Finding，Capsule，报告和拒绝通知；还有 MySQL 状态机、Transactional Outbox、
RabbitMQ 消费、Redis 租约与进度流、MongoDB checkpoint、MinIO 大对象、ES 检索、
租户鉴权、Web 控制台和 SpecCraft 运行时。

这些能力的“存在”不等于全部达到生产承诺。当前文档已经采用较诚实的 Go/No-Go 表，
明确只有一部分门槛有足够证据，Capsule 全量重放、独立归因准确率、生产试点、恢复演练、
KMS/HSM、跨语言执行等仍有缺口。因此终极目标不是“把 README 的数字继续加大”，而是
建立一套让每个数字都能被第三方复核的证据制度。

## 二、我对当前代码形态的阅读结论

### 2.1 主线代码地图

当前主线大致分为以下边界：

1. `agent/`：验证 Agent、LangGraph 节点、Worker、契约检查器、仓库图和安全扫描。
2. `craft/`：SpecCraft 的需求解析、计划、编辑、工具、收敛循环、验收交接和记忆。
3. `api/`：FastAPI 控制面、任务路由、Web 控制台聚合、Agent Console、Webhook、计费、
   统一错误封装、中间件和指标端点。
4. `storage/`：MySQL 事实源、Agent Job 持久化、租户身份、用量账本、MongoDB、Redis、
   RabbitMQ、MinIO、Elasticsearch、Outbox 和租户作用域。
5. `providers/`：OpenAI-compatible Provider、能力探测、推理模式、预算、工具 Envelope、
   Judge Persona、路由和结构化输出辅助。
6. `retrieval/`：符号索引、BM25、可选嵌入、RRF 融合、图谱邻域和重排降级。
7. `experiments/` 与 `sandbox/`：Java/Maven 执行适配器、沙箱命令、输出截断、探针工件和
   兼容性矩阵。
8. `evidence/`：报告、证书、契约血缘、工件摘要和拒绝通知。
9. `mcp/`：手写 MCP stdio JSON-RPC 服务和六个精简工具。
10. `apps/web/`：React/Vite/TypeScript 工作台，覆盖登录、Dashboard、验证任务、详情、
    矩阵、Finding、Contract、评测、健康和 Agent 工作区。
11. `services/control-plane/`：Spring Boot 控制面代码和迁移，承担部分租户、审计、
    Webhook、只读投影及可靠事件职责。
12. `infra/`、`docker/`、`.github/`、`scripts/`：Compose、观测栈、沙箱 Worker、种子、
    评测和 CI 门禁。

这个分层已经超过原始 Phase 0 的规模。它的优点是纵向切片多，缺点是边界开始出现重复：
Python FastAPI 和 Spring Control Plane 都有控制面职责，CLI、MCP 和 Web 有多套结果读取逻辑，
文件系统报告和数据库对象元数据并存，Agent Job 与 Verify Job 的状态模型尚未完全统一。
终极演进必须先解决“一个领域对象一个事实模型、多个入口复用一个应用服务”的问题。

### 2.2 验证主链路的代码事实

验证图在当前主线已经不是简单的十二节点示意，而是以 `agent/graph.py` 为编排核心，
在原有节点间加入仓库上下文检索和错误短路。典型链路为：

`intake → compile_contracts → prepare_base → prepare_head → collect_diff →
retrieve_repository_context → run_static_checks → generate_counterexamples →
run_differential → review_court → build_matrix → create_capsule → publish_report`。

每个节点应该只产生它负责的事实。`intake` 负责读取需求、校验仓库和规格路径；
`compile_contracts` 负责生成候选契约并标记来源；`prepare_base/head` 负责 worktree 隔离；
`collect_diff` 负责改变范围；`run_static_checks` 负责确定性源码证据；
`generate_counterexamples` 负责测试源码和编译记录；`run_differential` 负责相同测试在两份
版本上的执行和状态取证；`review_court` 负责把候选 Finding 按证据政策定级；
`build_matrix` 负责把 Contract 结果合并成需求到证据矩阵；`create_capsule` 负责打包；
`publish_report` 负责面向用户的报告。

这个责任划分非常关键。历史版本中曾出现节点覆盖 `contract_results`、静态分析结果被误
当作真实 PASS、只把测试注入 Head 而没有注入 Base、数据库变化从文件名推断、以及失败
节点继续生成报告的风险。现在主线已经通过结果合并、错误守卫、双版本注入和 H2 dump
部分修复这些问题。后续必须把这些不变量写成独立的领域测试，而不能只依赖某一个旗舰
案例通过。

### 2.3 Contract 编译的现状与边界

契约编译目前采用三层思路：确定性解析器先从需求文本里识别 AUTH、UNIQUE、TOKEN、
TRANSACTION、EVENT、OPENAPI 等家族；如果文本太稀疏且配置了 LLM，再用 Provider 生成候选；
最后在更完整的主线中通过 `agent/contracts` 的结构化解析、注册表和人工审批形成可批准
版本。这个设计的正确方向是“LLM 负责候选，组织策略负责批准，执行器负责验证”。

仍然需要补强的地方包括：候选 Contract 的版本不可变性、审批人与审批时间、来源文档
摘要、checker 版本、适用仓库范围、禁止变更、证据最低等级、撤销和替代关系，以及同一
需求跨多个提交的版本血缘。没有这些字段，后面做证书、豁免、租户策略和计费审计时会
重新依赖自由文本。

### 2.4 静态检查器的现实能力

`agent/checkers/java_source.py` 目前通过相对保守的 Java 源码切分和契约族检查实现了：
鉴权注解移除、事务边界削弱、重复邮箱保护移除、Token 失效移除、事件发布次数变化、
DTO 字段删除等检查。静态结果被限制在 MAJOR 以内，这是正确的证据政策：源码看到了
危险变化，但它没有证明请求一定能到达、状态一定发生改变、或者变化一定由 Head 引入。

静态检查器的长期方向不是无限增加正则，而是转为“语法树/符号图/规则 DSL/运行时探针”
组合。正则可继续作为快速预检和兼容回退，但必须明确 parser 版本、误报边界和语言适用
范围；对于复杂 Java 注解、重载方法、继承、代理、AOP、配置绑定和 SQL migration，应该
逐步引入 AST 或编译器级事实。

### 2.5 差分执行和证据的现实能力

Java/Maven 适配器已经把执行从“直接调用 mvnw”抽象为 `ExecutionAdapter` 协议，并对
Windows 绝对路径、离线 Maven 缓存、输出尾部截断、沙箱模式和探针工件做了考虑。现阶段
真正实现的第一适配器仍然是 Java/Maven；Gradle、Node、Python、Go 是兼容矩阵中的计划项，
不能对外宣称已经支持。

`run_differential` 的关键语义是同一个生成测试进入 Base 和 Head，分别记录退出码、测试
统计、标准输出尾部、H2 数据库快照和确定性 digest，再判断 COMPLIANT、REGRESSION、
AMBIGUOUS、UNEXPECTED_FIX 或 NON_REPRODUCIBLE。这个模型适合旗舰鉴权案例，但还没有覆盖
所有 Redis、RabbitMQ、并发、幂等、外部 HTTP、查询次数和性能语义。终极实验室需要把
“差异”从单一 JUnit 结果扩展成带 schema 的 Evidence Fragment 集合。

### 2.6 Review Court 和严重度政策

Review Court 有 Prosecutor、Defender、Judge 三个角色，也有确定性规则回退。BLOCKER 的
六条件包括批准 Contract、真实 Base/Head 执行、Head 归因、数据库或行为证据、Capsule
可重放以及置信度至少 0.90。静态证据被限制为 MAJOR。这条政策是产品可信度的核心，必须
保持硬约束，不能因为演示效果或模型意见把静态 Finding 升为 BLOCKER。

后续应将“法院”从三个 LLM prompt 提升为可审计判决协议：每个角色输入必须固定、候选
证据不能被模型改写、判决结果要引用证据 ID、未返回或解析失败默认不确认、最终严重度由
确定性政策再次校验。模型可以提出理由，不能绕过政策。

### 2.7 可靠性内核的现实状态

MySQL 负责 Job 状态、Contract、Finding 和 Outbox；RabbitMQ 负责 at-least-once 事件；
Redis 负责幂等键、租约、预算和进度 Stream；MongoDB 负责 checkpoint 和复杂 Evidence Pack；
MinIO 负责大文件；Elasticsearch 负责检索。这种职责划分是合理的。

当前风险不在于“有没有适配器”，而在于跨适配器事务边界、恢复演练和长期运维证据：
Outbox 已有可靠性测试，但需要持续验证 relay 崩溃窗口；Worker 需要取消检查点、租约
续租指标和终态幂等；MongoDB 与 MinIO 的工件链需要定期扫孤儿和悬挂引用；Redis 进度流
要定义保留期、断线重连边界和大任务背压；数据库迁移必须支持空库安装和兼容升级。

### 2.8 SpecCraft 的现实状态

SpecCraft 已经具备需求解析、确定性计划、工具注册表、原子编辑、备份、审计、执行、
五道自校验门、预算、循环收敛、Agent Job 投影和 Web SSE 事件。`api/agent_runtime.py`
把确定性 CraftLoop 接入 Agent Console，使“新建任务→计划→工具流→门禁→终态”成为可点的
本地流程；LLM 规划和诊断则通过 Provider 能力和预算控制接入。

终极目标不是让 CraftLoop 自己越来越会改文件，而是让它形成受控的“计划审批→受限编辑→
测试→独立验收→修复循环”。写集冲突、危险命令、越权路径、超出目标范围、预算超限、
Prompt Injection 和用户中断都必须有显式状态，而不能只在异常日志里体现。

## 三、终极目标：把“代码交付”变成“证据交付”

### 3.1 终极产品定义

最终产品应当是一个本地优先、可私有部署、可接入任意编码 Agent 的 AI 变更验收平台，
并带有一个受控的开发 Agent。它的核心交付物不是评论，而是四类可验证对象：

1. **Contract**：经过版本化和批准的需求约束，明确可观察行为、禁止变化和证据要求。
2. **Experiment**：在指定执行环境中运行的实验，输入、命令、资源、版本和输出可追溯。
3. **Evidence Pack**：把测试、日志、状态快照、差分、digest、工具链和环境绑定起来。
4. **Certificate / Rejection**：只在所有必要约束满足时签发，否则给出带原因的拒绝或待审。

SpecCraft 的交付物则是：计划、编辑审计、测试结果、独立验收结果、补丁/分支和预算账本。
它不能直接生成“已通过”证书。平台把“开发速度”和“验收可信度”分成两个可量化方向，
从制度上避免把模型自评当作质量证明。

### 3.2 终极用户链路

用户从 GitHub PR、CLI、Web 向导、MCP 或本地 Agent 发起验证。系统先解析提交、需求和
仓库策略，创建不可变 Job 和输入摘要；然后加载或创建 Contract 版本，等待人工审批或
使用已批准策略；调度 Worker 在隔离沙箱中准备 Base/Head，执行静态、动态、状态、变异、
兼容性和性能实验；所有实验以 Evidence Fragment 写入对象存储和数据库；Review Court
按政策确认 Finding；矩阵把每条需求映射到结果；用户在 Web 中查看、下载和重放；最后通过
门禁向 GitHub Check、MCP 客户端或 CLI 返回 VERIFIED、BLOCKED、FAILED、NEEDS REVIEW 或
等待人工状态。

如果用户选择 SpecCraft，则先创建 Craft Job，加载仓库规则和任务规范，进入 PLAN_READY
等待批准；批准后在沙箱中执行工具，持续发布事件和审计；完成后自动生成验收 Job；若
验收失败，系统可以把 Capsule 和最小修复建议交回 Craft，最多按预算进行有限闭环；任何
超出范围、危险操作或模型无法解释的行为都停止并请求人工决定。

### 3.3 终极质量指标

终极指标必须从“演示数字”升级为“长期运营数字”：

- 关键 Finding Precision 至少 95%，严重级别 Precision 至少 90%。
- 语义回归 Recall 至少 90%，并单独报告不同契约族的 Recall。
- Head 归因准确率至少 95%，Base 预存缺陷不能被误报成 PR 引入。
- Capsule 全量独立回放成功率至少 99%，回放失败必须可分类为环境、工件、脚本或产品缺陷。
- 严重 Finding 无证据率为 0；`UNVERIFIED` 不得被任何入口隐式显示为 PASS。
- Worker kill、Provider 超时、RabbitMQ 重投、Outbox 崩溃、对象链断裂等故障演练恢复率 100%。
- 关键 API p95、验证小 PR p95、队列等待、LLM 成本和沙箱资源都有可追踪 SLO。
- SpecCraft 任务完成率至少 90%，陷阱变体拦截率 100%，预算内完成率至少 80%，平均迭代数受控。
- 评测集至少 200 个案例，正负样本、holdout、Prompt Injection、等价重构、环境故障和
  跨版本兼容都覆盖；任何数字都要有原始结果文件和生成命令。

## 四、目标架构：从“多功能仓库”收敛为“一个领域内核、多个入口”

### 4.1 领域内核

建议未来明确六个领域模块，不再让路由、CLI、MCP 直接拼装底层 SQL 或解析 CLI 文本：

1. `identity`：组织、租户、用户、角色、权限、API Key、Webhook 身份和租户作用域。
2. `verification`：Verify Job、输入快照、Contract 版本、Experiment、Finding、矩阵、终态。
3. `execution`：仓库快照、适配器、沙箱、资源预算、探针、状态采集和执行证据。
4. `evidence`：Evidence Pack、对象元数据、digest、血缘、Capsule、证书和撤销状态。
5. `craft`：Craft Job、计划 DAG、工具调用、编辑审计、自校验、交付和验收交接。
6. `billing`：事件计量、预算、配额、账单、发票和套餐策略。

每个领域有自己的命令、应用服务、仓储接口、事件 schema 和权限矩阵。FastAPI、Spring
Control Plane、CLI 和 MCP 只做传输适配；Web 只消费聚合 DTO。这样才能避免现在存在的
“一个入口从文件系统找 Capsule、另一个入口从 MySQL 找路径、第三个入口解析 CLI stdout”
逐渐产生不一致。

### 4.2 单一事实源和投影

MySQL 是 Verify/Craft Job、状态机、Contract 审批、Finding 摘要、租户和用量的事实源。
MongoDB 是可重建的 checkpoint 和复杂分析文档，不得成为 Job 终态的唯一来源。MinIO 是
大对象内容，MySQL 只保留对象元数据、digest、大小、媒体类型、保留策略和访问权限。
Elasticsearch 是可删除、可重建的检索投影。Redis 是有 TTL 的锁、租约、进度和预算缓存。
RabbitMQ 是事件传输，不是查询数据库。

所有读取端点都应该从一个应用服务取得经过租户过滤的聚合对象；所有异步事件都带
`event_id`、`event_type`、`schema_version`、`tenant_id`、`aggregate_id`、`occurred_at`、
`trace_id`、`producer`、`payload_digest` 和 `idempotency_key`。任何投影都可以从 MySQL
或事件重建，任何无法重建的数据必须明确标为不可恢复。

### 4.3 Verify Job 状态机

验证 Job 建议冻结为：

`QUEUED → PREPARING → CONTRACT_REVIEW → RUNNING → REVIEWING →
VERIFIED | BLOCKED | NEEDS_REVIEW | FAILED | CANCELLED | STALE | EXPIRED`。

状态转换必须由服务端白名单控制；每次转换写审计和事件；`FAILED` 只表示系统无法完成
验证，不表示代码一定有问题；`BLOCKED` 表示确认存在阻断性回归或策略禁止；
`NEEDS_REVIEW` 表示发现或契约证据不足，需要人工判断；`STALE` 表示 Head 已被新 Job 替代；
`CANCELLED` 只能由用户或管理员明确触发；`EXPIRED` 表示超过保留或执行期限。

### 4.4 Craft Job 状态机

SpecCraft 建议使用：

`QUEUED → PLANNING → PLAN_READY → EXECUTING → SELF_VERIFYING → HANDOFF_VERIFY →
DONE | FAILED | STUCK | CANCELLED | EXPIRED`。

PLAN_READY 是真正的人机协同点。计划中要展示目标文件、命令、风险、预计成本、禁止
操作、可能触发外部服务的步骤和预计变更规模。只有计划批准后才允许写入。每个工具调用
写 `tool_call`、`tool_result`、输入摘要、输出摘要、资源消耗和决策来源。自校验通过也只
能把 Job 推到 HANDOFF_VERIFY，由独立 SpecProof 创建验证任务。

### 4.5 入口统一

CLI 用于本地脚本和 CI；FastAPI 用于 Web 和系统集成；MCP 用于外部编码 Agent；GitHub App
用于 PR 触发和 Check Run；Spring Control Plane 用于需要 Java 生态或组织级可靠事件的
部署形态。五种入口必须调用同一 `VerificationApplicationService` 和
`CraftApplicationService`，统一错误码、权限、幂等和响应字段，而不是各自实现一套逻辑。

## 五、从请求到证书的完整目标链路

### 5.1 输入阶段：建立不可变 Job

输入包括仓库地址或本地路径、Base SHA、Head SHA、需求文本或 Issue、组织策略、执行深度、
预算和租户。服务先进行路径规范化、仓库权限检查、提交存在性检查、大小限制和密钥策略
检查，然后计算输入摘要。需求文本、PR 描述、README、代码、测试和配置全部视为不可信
数据；它们可以被引用和检索，但不能覆盖系统级安全规则。

Job 创建和 Outbox 写入必须在同一 MySQL 事务中完成。返回客户端的不是“开始了”这句空话，
而是 `job_id`、`input_digest`、`policy_version`、`contract_version`（如果已知）、当前状态、
幂等键和预计资源。重复请求使用同一幂等键返回原 Job，不再产生第二个 Outbox 事件。

### 5.2 需求阶段：Contract 编译与审批

需求编译器先做确定性结构化解析：角色、动作、资源、前置条件、成功结果、失败结果、
不变量、禁止变化、性能约束和兼容约束。再按领域映射到 Contract family，例如 AUTH、
TRANSACTION、UNIQUE、IDEMPOTENCY、EVENT、CACHE、MIGRATION、OPENAPI、CONCURRENCY、
BOUNDARY、NPLUSONE、TEST_STRENGTH。

LLM 可补充候选和自然语言归一化，但必须输出 Pydantic 模型，经过 schema 校验、来源摘要
和风险检查。模型不能直接设置 APPROVED。批准操作由用户、组织策略或已审计自动策略完成，
产生不可变版本。任何 Contract 的修改都产生新版本，旧版本继续可重放，不能原地覆盖。

### 5.3 仓库与上下文阶段

系统读取 `AGENTS.md`、`CLAUDE.md`、README、ADR、测试和策略文件，建立有优先级的规则集：
系统安全规则最高，组织策略其次，仓库规则再次，用户任务和模型建议更低。仓库文本只进入
数据段，不能伪装成系统指令。索引层以 commit SHA 和 tenant/repository 强制隔离，避免把
其他仓库的私有代码召回给当前任务。

检索默认 BM25 加符号图谱；配置嵌入时使用向量检索和 RRF；有交叉编码器或 LLM 时可重排；
没有依赖时保序降级。每次返回都标注 `retrieval_mode`、`embedding_used`、`rerank_mode`、
命中数量和降级原因，不能给用户一个没有来源的“相关上下文”数组。

### 5.4 Base/Head 准备阶段

仓库以只读输入方式挂载或复制到执行工作目录，Base 和 Head 使用隔离 worktree。所有
subprocess 都使用参数数组，禁止拼接 shell；路径必须通过根目录约束和 resolve 检查；
引用必须满足提交、分支或标签格式并在仓库中可解析。准备失败直接进入 FAILED，不再运行
后续节点。

执行器根据仓库探测结果选择适配器。Java/Maven 是当前实际支持的第一适配器，其他语言
必须通过兼容矩阵显式显示 NOT_IMPLEMENTED。每次执行记录镜像、digest、JDK/Maven 版本、
离线策略、网络策略、用户 UID、pids limit、CPU/内存、输入工作区摘要和命令摘要。

### 5.5 静态和动态实验阶段

静态实验包括源码差分、AST/符号检查、OpenAPI diff、migration diff、依赖策略、秘密扫描、
测试强度和架构规则。静态发现默认最高 MAJOR，除非有动态证据升级。

动态实验由 Contract 选择模板：HTTP 认证、数据库唯一性、事务回滚、Redis TTL/失效、
RabbitMQ 发布/重投、幂等、状态机、并发和性能。每个模板都有输入、前置播种、操作、断言、
采集器和预期证据 schema。生成测试必须经过语法/依赖/范围校验，编译失败不能被“自动修复
成功”叙述掩盖。

### 5.6 差分判定阶段

同一实验在 Base 与 Head 执行。系统比较：退出码、测试统计、HTTP status/body/header、
数据库行、Redis key/TTL、RabbitMQ routing key/payload/count、外部调用次数、查询数、
异常类型、OpenAPI schema 和性能分位数。差异分类为预期变化、回归、修复、歧义或不可复现。

每个 Evidence Fragment 只描述实际观察到的内容。比如没有抓到 Redis 状态，就返回
`REDIS_NO_EVIDENCE`；不能根据代码中出现 `delete` 就填“Token 已失效”。数据库状态应来自
H2 dump、Testcontainers 查询或受控数据库快照，而不是测试文件名或模型解释。

### 5.7 Review Court 阶段

法院输入候选 Finding 和 Evidence ID，不直接接受模型生成的证据。Prosecutor 说明为何是
真实问题；Defender 说明可能的预存缺陷、等价重构、环境噪音或测试不充分；Judge 给出判决。
确定性政策随后重新检查严重度、Contract 审批、Head 归因、真实退出码、DB/行为证据、
Capsule 可构建和置信度。任何条件缺失都降级或进入 NEEDS_CONFIRMATION。

### 5.8 证据、矩阵和终态

矩阵每一行对应一个不可变 Contract 版本，字段至少包括：需求摘要、适用版本、变化符号、
实验 ID、Base 结果、Head 结果、差分归因、证据引用、结论、置信度、降级说明、审阅者和
判定时间。结果优先级固定为 `FAIL > PASS > UNVERIFIED`，多个节点不能覆盖彼此事实。

只有所有必需 Contract 都是有证据的 PASS、没有未确认严重 Finding、没有错误、策略允许
签发时才进入 VERIFIED；否则生成 Rejection Notice 或 NEEDS_REVIEW。证书必须包含仓库、
Head SHA、需求摘要、Contract 摘要、Evidence 摘要、工具链摘要、策略版本、签发者、时间、
证书版本和签名。SHA-256 只是摘要，Ed25519 才是身份签名；密钥应进入 KMS/HSM 或至少
受保护的本地签名服务，绝不能写入仓库或普通日志。

### 5.9 Capsule 阶段

Capsule 包括 manifest、requirement、contract、finding、生成测试、fixtures、Base/Head
结果、工具报告、环境描述、run.sh、run.ps1、README、对象摘要和版本信息。脚本不能默认
修改用户工作树；应创建临时 worktree，完成后清理，失败时保留明确路径。回放结果要生成
新的 replay record，并比较原 Evidence Digest 与当前观察，区分“相同结论”“相同输入但
环境不同”“证据不一致”“无法回放”。全量 Capsule 需要定期批量演练。

## 六、各技术域的终极演进方案

### 6.1 Provider 与模型治理

当前 Provider 的方向是正确的：不相信网关文档，第一次调用前做能力探测；统一
`ModelProvider` 接口；支持 chat、streaming、JSON output、tool calls、thinking、
reasoning、usage、error codes 和 rate-limit headers；当 strict tool calls 不可用时使用
JSON Action Envelope；思考模式与工具调用冲突时分层处理。

下一步应做四件事。第一，把 Probe 结果写成带时间、模型、端点摘要、能力版本和有效期的
不可变记录；同一 Job 固定使用同一 Provider profile，避免中途切换造成不可解释差异。第二，
所有 LLM 输出进入 Pydantic 校验器，失败后一次结构化修复重试，再失败回退确定性模板。第三，
按租户、Job、节点和模型建立 token/cost ledger，预算在调用前预检、调用后核算，不能只依赖
模型返回 usage。第四，路由器按照能力、成本、延迟、数据驻留和租户策略选择模型，但验证
证据链中的关键步骤默认固定模型与版本，计划/诊断等非证据链路才允许语义缓存。

推理内容要有独立保留策略。它可以用于调试和质量研究，但默认不写入 Evidence Pack，防止
把敏感仓库或密钥片段带进证据。模型输出永远不是权威事实；能进入证据的只有经过工具
执行、schema 校验和权限检查的结果。

### 6.2 Contract Compiler 与策略即代码

建立 Contract DSL，至少支持：

- `id`、`version`、`family`、`requirement_digest`、`approval_state`；
- `scope`（仓库、语言、框架、路径和符号）；
- `preconditions`、`action`、`expected_observations`、`forbidden_observations`；
- `evidence_minimum`、`severity_policy`、`timeout`、`resource_budget`；
- `checker_version`、`source_refs`、`supersedes`、`revoked_at`。

契约编译应采用“候选—审阅—批准—锁定—执行—复盘”生命周期。每个 Contract family
都配套 deterministic checker、execution template、evidence schema、golden cases 和
失败样本。组织策略可以规定某类 Contract 必须真实动态执行，某类只能在特定沙箱运行，
某类结果只能由安全组审批。策略 DSL 不应允许把严重度门槛调低到绕过证据政策。

### 6.3 执行适配器和沙箱

执行适配器要遵循 `detect/prepare/run/collect/cleanup` 协议。Java/Maven 继续作为第一
实现，随后按价值接入 Gradle、Python、Node、Go；每种适配器有独立镜像、缓存、测试矩阵和
已知限制。适配器不应把命令构造和证据采集混在一起，便于增加状态探针和模拟器。

沙箱默认非 root、无网络、只读源码、可写 target/tmp、pids limit、CPU/内存限制、无宿主机
Docker socket、无宿主机环境和密钥、输出长度上限、超时 kill 和子进程清理。DooD 或等效
容器运行只允许在明确隔离的 Worker 服务中使用，不能把宿主 Docker Socket 直接暴露给不可信
仓库。Windows 本地开发可以有显式 local fallback，但 UI 和报告必须显示“本地模式，隔离
弱于容器模式”，不能与生产沙箱等同。

沙箱威胁模型要覆盖恶意 Maven/Gradle 插件、构建脚本、测试 fork、符号链接、路径穿越、
资源耗尽、输出洪水、DNS/IPv6 绕过、临时目录残留、缓存投毒、镜像供应链和秘密侧信道。
每一条威胁都要有测试、监控和应急处置，而不是只在 README 中声明“安全”。

### 6.4 状态差分实验室

把当前 `diff_results` 拆为标准 Evidence Fragment：

`HttpObservation`、`DbObservation`、`RedisObservation`、`MqObservation`、
`SchemaObservation`、`PerformanceObservation`、`StaticObservation`、`BuildObservation`。

每个观察都有 `base`、`head`、`normalization`、`comparison`、`evidence_ref`、`collector_version`
和 `reproducibility`。比较器要支持字段忽略、顺序归一化、敏感字段脱敏、随机值遮罩、
时间容差和并发波动区间。对于无法可靠比较的部分，返回 AMBIGUOUS，而不是强行判断。

### 6.5 Mutation 与 Fuzzing

变异测试只针对 PR 影响范围和已批准 Contract。变异算子包括条件反转、边界值、返回值、
空值处理、权限注解、事务边界、重试、Ack、幂等和缓存失效。结果分为 KILLED、SURVIVED、
TIMEOUT、BUILD_FAILED、EQUIVALENT_CANDIDATE。存活变异体不自动成为 Bug，而是触发测试
强度分析或人工复核。

OpenAPI 状态化 Fuzzing 要从 schema、前置资源、鉴权状态和序列化关系生成最小失败序列；
并发测试要记录线程数、调度策略、数据库隔离级别、重试次数和重复副作用。所有 Fuzzing
都必须绑定预算和最小化器，防止一个坏输入让 Worker 无界运行。

### 6.6 RAG 与上下文工程

索引对象分为代码符号、文档、Contract、历史 Finding、测试和证据摘要，并强制 tenant、
repository、commit 和访问策略过滤。召回链是 BM25 + 可选向量 + RRF + 符号图谱邻域 +
可选重排 + 预算截断。每次索引记录 parser、embedding、schema 和 commit 版本；索引可删除、
可重建、可审计。

评测必须有黄金上下文集，至少测 recall@10、MRR、契约命中率、跨租户泄露率和 Prompt
Injection 影响率。上下文模板采用稳定前缀、任务模板、变量数据结构，以提高 KV cache
命中和可重复性。压缩摘要要能回溯原始消息和 checkpoint；不能把压缩后的模型总结当作
唯一证据。

### 6.7 SpecCraft 开发 Agent

SpecCraft 的终极循环是：读取任务和仓库政策，生成结构化计划，展示风险和写集，等待批准，
执行受限工具，保存每步 checkpoint，运行测试和自校验，产生 diff 和验收申请。工具分为
读、搜索、编辑、测试、构建、版本控制和外部集成七类，每类有风险级别、参数 schema、
超时、输出限制和权限。工具输出必须被包装为不可信数据；任何“忽略之前指令”“上传密钥”
等文本都不能改变系统策略。

子代理并行先从只读任务开始。可写并行需要文件所有权、写集声明、锁、冲突检测和父任务
合并审阅；没有这些条件就 fail-closed。上下文超限时生成压缩点并记录输入摘要，恢复时
重新加载原始任务、计划和最近证据。模型无法继续、连续工具失败、修改范围膨胀、预算即将
耗尽都进入 STUCK 或人工暂停，而不是继续随机试错。

### 6.8 API、Web 和 MCP

API 统一采用版本化路径、请求 ID、trace ID、稳定错误 Envelope、租户作用域、限流和审计。
Job 创建、查询、取消、进度、矩阵、Finding、证书、Capsule、Contract、评测、健康和计费
必须有明确权限。SSE 支持 Last-Event-ID，断线后只补发未确认事件；事件太旧时返回重置
提示而不是无限轮询。

Web 重点是工作流，而不是堆页面：新建验证向导、任务详情时间线、矩阵对照、Finding 证据、
Capsule 重放、Contract 审批、Agent 计划审阅、权限拒绝、降级态、取消和失败恢复都要有
真实交互。所有按钮显示当前状态和风险，禁止把 loading、空结果、权限不足和服务降级都
做成空白页面。

MCP 工具保持精简。当前六工具方向是合理的：verify、contracts_list、eval_summary、
craft_plan、health、replay_info。未来扩展必须先证明无法通过现有工具组合完成；所有参数
强校验、路径限制、超时、输出截断和错误结构化。MCP 不应暴露任意 shell 或任意数据库查询。

### 6.9 证据血缘与签名

证据链以对象引用和 digest 组成有向无环图：需求版本 → Contract → 代码提交 → 实验输入 →
执行工件 → Finding → Matrix → Capsule → Certificate。每个节点有创建者、版本、来源、
租户、保留期和撤销状态。证书包含根摘要和所有关键节点摘要；任何对象替换都导致验证失败。

签名服务应与 Worker 隔离，私钥不可被执行不可信代码读取。证书需要支持离线验证、公钥轮换、
撤销列表、时间戳和密钥版本。KMS/HSM 未完成前只能称为 digest attestation，不可称为正式
签名证书。这个措辞必须在 UI、API、MCP、文档和面试材料中统一。

### 6.10 计费、配额和成本

用量账本记录 verify 次数、执行秒数、沙箱资源、LLM 输入/输出 token、嵌入、对象存储、
保留期和 Craft 工具调用。每个计量事件有 event_id、tenant_id、job_id、meter_type、
quantity、unit_price、currency、source、created_at 和幂等键。账本可由事件重建，发票可
追溯到原始事件，修正使用冲正事件而不是 UPDATE 历史行。

预算在 Job 创建和每次高成本步骤前预检；达到阈值进入 WAITING_BUDGET 或 CANCELLED，不让
模型继续调用。验证证据正确性不能被账单服务故障阻断：账单写失败进入可靠队列并告警，
但 Job 结果仍依据验证事实完成。

## 七、分阶段实施路线

下面的阶段不是简单按模块堆功能，而是按“先收口事实模型，再扩展实验面，再做商业化”排序。
每个阶段必须有入口条件、可验证产物、退出门禁和不做事项。

### 阶段 0：主线治理与可信基线，1 周

目标：停止多副本漂移，建立唯一主线、版本规则、证据目录和当前指标基线。

工作项：

- 把 `specproof-clean-clone-gate` 标为唯一主线；为其他目录写 `EXPERIMENT.md`，注明来源、
  基准提交、是否可运行、是否禁止直接复制。
- 建立 `docs/architecture/domain-model.md`、数据字典、状态机图和入口矩阵。
- 固定 Python、Node、Java、Maven、Docker Compose 和数据库兼容版本；生成依赖锁定摘要。
- 建立 `make/check.ps1` 或等价本地门禁，但不自动执行 Windows 安装包、Docker 镜像构建、
  Git 提交或推送。
- 记录全量 unit、security、fault、integration、golden、frontend build 和 API 冒烟的原始
  结果文件；把历史报告和当前重跑结果分开。
- 扫描仓库中的密钥、`.env`、日志、Capsule 和报告，确认真实凭据从不进入产物。

退出条件：主线可从干净 clone 安装；至少能执行确定性 verify；所有历史数字有来源；
根目录实验副本不再被 CI 误扫描；发现当前测试红线时有明确责任和阻断说明。

不做：不引入新语言适配器，不启动公网部署，不做 Windows 安装包，不做 Docker 镜像发布。

### 阶段 1：领域内核与 Job 事实源，2 周

目标：让 CLI、API、MCP、Worker、Web 共享同一 Verify/Craft Job、Contract、Finding、Artifact
和事件模型。

工作项：

- 冻结 Job 状态机和合法转换表；所有转换使用应用服务。
- Contract registry 增加不可变版本、审批、撤销、checker_version、evidence_minimum 和血缘。
- 统一事件 Envelope、错误码、请求 ID、trace ID、租户作用域和幂等键。
- 让 Web/API/MCP 从应用服务取聚合数据，不再解析 CLI stdout 作为长期协议。
- 将文件报告、Capsule、证书改为对象元数据引用；保留本地文件 fallback 但标注来源。
- 为 Verify Job 和 Craft Job 建立独立但可关联的 `verification_request_id`。

退出条件：重复请求不重复创建 Job；跨租户读取为 404/403；所有入口得到相同状态和矩阵；
状态机故障注入覆盖重复、乱序、并发和非法转换；迁移可从空库执行。

### 阶段 2：证据链和回放闭环，2-3 周

目标：把 Capsule、Evidence Pack、对象链和证书从“文件生成”提升为“可验证产品能力”。

工作项：

- 定义 Evidence Fragment schema 和 collector version。
- 每个严重 Finding 强制关联实验、输入、输出、环境、digest 和 replay command。
- 建立全量 Capsule replay runner，批量执行 run.sh/run.ps1，统计成功率和失败分类。
- Capsule 使用临时 worktree，支持无污染回放，输出 replay record。
- 实现证书离线验证和 digest mismatch 报告；在 KMS 之前明确只称摘要证明。
- 增加 MinIO/Mongo orphan、dangling reference、sha mismatch 扫描和保留期清理演练。

退出条件：现有全部严重 Capsule 有真实回放统计；回放结论与原始结论可比较；证据链破坏
会被发现；没有证据的严重 Finding 为零。

### 阶段 3：动态实验室扩展，3-5 周

目标：从鉴权/H2 旗舰案例扩展到业务状态和消息语义。

工作项：

- 增加 Redis snapshot/TTL/失效实验和可控播种。
- 增加 RabbitMQ publisher confirm、routing key、payload、重复投递和 consumer idempotency
  探针。
- 增加事务回滚、并发、唯一约束、幂等、缓存一致性和 OpenAPI schema diff 模板。
- 统一三表或多表 H2/Testcontainers 状态快照，避免每个案例各写一套解析。
- 让 `contract_id` 从需求到实验到矩阵一贯传递，不再用 `DIFF-01` 作为泛化兜底。
- 建立故障注入：服务崩溃、超时、网络断开、消息重投、DB 锁等待、对象上传成功后写库失败。

退出条件：每个新增契约族都有正样本、负样本、holdout 和可重放 Capsule；Base 预存缺陷不
被错误归因；动态证据覆盖目标场景；实验预算和超时可控。

### 阶段 4：Mutation、Fuzzing 和跨语言适配器，4-6 周

目标：提升测试发现能力，并把执行器从 Java/Maven 单一实现演进为可扩展协议。

工作项：

- 完成 Mutation-guided test synthesis，先做 Java/PIT 或源码算子的小范围战役。
- 增加 OpenAPI 状态化 Fuzzing 和最小失败输入。
- 实现 Gradle 或 Python 其中一个高价值适配器，建立兼容性矩阵和限制说明。
- 适配器输出统一 RuntimeProfile、ExecutionResult、EvidenceFragment。
- 评估 Node/Go，不以“检测到 package.json/go.mod”冒充已支持执行。

退出条件：Mutation 结果能区分等价、存活和测试弱点；Fuzzing 有预算和最小化；跨语言
适配器有真实 CI/沙箱证据；不支持的项目明确 fail-closed。

### 阶段 5：企业安全、签名和恢复，3-5 周

目标：让平台能够面对私有仓库、企业身份和真实故障。

工作项：

- OIDC/企业 SSO、SCIM 或组织成员同步、RBAC/ABAC、租户级限流和密钥轮换。
- KMS/HSM 签名、公钥轮换、证书撤销和离线 verify。
- 对象加密、数据库备份、恢复点目标、租户删除和数据导出。
- 做 Worker kill、MySQL 故障、Mongo 恢复、RabbitMQ 重投、Redis 丢失、MinIO 孤儿和
  Provider 长时间不可用的演练。
- 建立事故模式：暂停新任务、冻结证书、隔离租户、撤销密钥、保留证据和恢复服务。

退出条件：恢复演练有真实记录；证书能验证签名和撤销；权限边界有跨租户测试；备份能够
恢复到可查询状态；所有敏感数据有保留和删除策略。

### 阶段 6：用量、配额和商业运营，2-4 周

目标：让本地/私有部署也有可解释的成本控制，为 SaaS 做准备但不牺牲证据。

工作项：

- 完成 usage ledger 的 API、后台对账、月账单和异常冲正。
- 为验证深度、并发、保留期、LLM、嵌入和沙箱时长定义可解释套餐。
- 超额状态、预算预警、管理员配额和审计。
- Dashboard 展示真实消耗、降级原因、估算与最终结算的差异。

退出条件：任何账单数字可从事件重建；账单故障不改变验证结论；配额超限不会继续产生
不可控 LLM 调用；租户可以导出自己的用量。

### 阶段 7：SpecCraft 生产闭环，4-8 周

目标：把开发 Agent、独立验收和有限修复组成可人工控制的闭环。

工作项：

- PLAN_READY 审批、危险命令确认、范围守卫、文件写集和撤销。
- 任务失败时从 checkpoint 恢复，支持取消和过期。
- Craft 完成后自动创建 Verify Job，引用其 commit、需求和变更范围。
- Verify 失败时只生成证据化修复建议或受批准补丁，不自动推主分支。
- 增加 10 任务确定性/LLM 微基准、陷阱变体、预算和恢复指标。
- 先做只读子代理并行，再评估可写并行。

退出条件：Agent 可以完成受控任务；用户能在计划、编辑、测试、验收、交付每一步介入；
所有改动有审计和 Diff；独立验收永远不被 Craft 自评绕过。

### 阶段 8：生态和持续运营，长期

目标：GitLab、IDE、MCP 客户端、通知连接器、插件、行业 Contract 包和多区域部署。

前提是阶段 0-7 的数据模型、权限、证据和评测稳定。任何生态扩展都必须遵守插件权限、
版本兼容、资源预算、审计和撤销，不允许因为“生态”重新引入任意 shell、任意网络或跨租户
数据读取。

## 八、90 天可执行排期

### 第 1-2 周：收口

完成主线标记、实验副本说明、领域模型、状态机、事件 Envelope、当前门禁报告和数据字典。
每天只允许一个垂直切片进入主线；测试先行；不做安装包、镜像发布、提交推送和公网部署。

### 第 3-4 周：统一入口

完成 Job/Contract/Finding/Artifact 应用服务，CLI/API/MCP/Web 使用同一服务；补跨租户、幂等、
错误 Envelope、迁移和状态机测试。将文件路径协议替换为对象元数据协议，同时保留兼容读取。

### 第 5-6 周：证据回放

完成 Evidence Fragment schema、Capsule 批量回放、replay record、血缘校验、孤儿对象扫描、
证书离线 digest 校验。用现有 10/20/100 案例先跑小批量，再扩全量。

### 第 7-9 周：动态实验

优先 Redis、RabbitMQ、事务、唯一性和 OpenAPI；每一类先写三类案例：正样本、负样本、
holdout。把测试模板和采集器做成可复用协议，不再让案例脚本各自解析日志。

### 第 10-11 周：沙箱与恢复

把非 root、无网络、资源限制、缓存策略、适配器状态和本地 fallback 的差异写进报告；完成
至少五种故障演练。Windows 只做本地执行回归和文档验证，不跑 Windows 安装包链路，除非
收到明确指令。

### 第 12-13 周：用户闭环

完成 Web 验证向导、计划审批、Finding 证据、Capsule 下载/重放、权限拒绝、取消、失败恢复、
用量和健康状态；补 Playwright 真实 e2e。最后重新跑全量门禁和 Go/No-Go，生成一份不夸大的
发布候选报告。

## 九、评测与门禁体系

### 9.1 评测分层

评测不能只看一个 100 案例总分，应分为：

1. 单元：纯函数、schema、状态机、解析、预算和工具。
2. 安全：密钥、路径、权限、跨租户、Webhook 重放、Prompt Injection、沙箱边界。
3. 故障：Outbox、RabbitMQ、Worker、Provider、SSE、Mongo/MinIO、数据库和取消。
4. 合同：每个 Contract family 的 checker 和实验模板。
5. Golden：正/负/holdout/等价重构/预存缺陷/环境噪声。
6. 集成：真实 MySQL、Redis、RabbitMQ、Mongo、ES、MinIO 和 API。
7. e2e：CLI、Web、MCP、GitHub Webhook 和 SpecCraft 闭环。
8. 性能：排队、执行、LLM、检索、对象、报告和并发。

### 9.2 每次改动的最小验证

契约或验证核心改动：先跑对应 unit、checker、golden 子集，再跑 integration differential，
最后跑全量 eval。存储改动：先跑适配器 unit，再做真实服务迁移和故障测试。API/Web 改动：
跑 route unit、OpenAPI diff、Playwright 受影响场景。沙箱改动：跑安全边界、适配器和容器
探针；不把“compose config 通过”当作沙箱安全证明。Provider 改动：跑 mock capability、
真实端点 probe（用户明确允许时）和成本预算测试。

### 9.3 质量红线

- 任意真实 API Key、Token、私钥进入仓库、日志、报告、Capsule 或 Prompt：立即阻断。
- 任何静态 Finding 被错误升为 BLOCKER：阻断合并。
- 任何错误、未执行 Contract 被显示 PASS：阻断合并。
- 任何跨租户读取、任意路径或任意 shell：阻断合并。
- Worker 重试产生重复 Finding、重复消息或重复计费：阻断合并。
- Capsule 无法从干净环境回放且没有明确环境分类：不得宣称证据完成。
- 任何测试只验证文件存在、服务启动或 HTTP 200，却没有验证业务语义：只能算烟雾检查。

## 十、主要风险、替代方案与决策边界

### 风险一：功能面过大导致核心可信度被稀释

当前仓库已经同时包含验证、防火墙、开发 Agent、RAG、前端、MCP、计费、GitHub、沙箱和
多中间件。继续并行加功能会增加状态、权限、迁移和测试成本。替代方案是把主线分成
`core-verifier`、`craft`、`platform` 三个发布层，先确保 core-verifier 的证据和回放稳定，
其他层通过 API 接入。

### 风险二：Python FastAPI 与 Spring Control Plane 双控制面漂移

两者都可能处理 Job、Webhook、租户和 Outbox。短期可以保留，但必须明确一个是外部入口、
一个是可靠投影或组织服务，并共享事件 schema、迁移和状态转换契约。长期若没有明确边界，
应选择一个控制面作为事实写入方，另一个只做适配或逐步退役。

### 风险三：LLM 生成测试不稳定

LLM 可能生成无法编译、短路断言、错误包名或只测 Head 的测试。解决方法不是不断加 Prompt，
而是 schema 校验、编译循环、范围校验、双版本注入、测试来源记录和确定性模板回退；无法
生成时返回 UNVERIFIED，绝不伪造动态证据。

### 风险四：动态环境导致证据不可重放

外部网络、时间、随机数、消息顺序、数据库初始状态和依赖版本都会改变结果。应为实验提供
固定镜像、离线缓存、fixture、种子、时钟/随机源控制、状态清理和环境摘要；不能做到时把
结论标成 AMBIGUOUS 或 NON_REPRODUCIBLE，并在报告里说明差异。

### 风险五：沙箱安全承诺超过实际隔离

DooD、Windows local fallback、共享缓存和本地进程都可能弱于 Linux 容器隔离。报告和 UI 必须
显示 execution mode、网络、用户和资源限制。生产严重 Finding 的证据只能来自达到政策等级
的沙箱；本地 fallback 结果可以用于开发，不应自动升级为发布证明。

### 风险六：计费侵入验证正确性

如果每次 LLM 调用或对象上传都同步依赖计费数据库，账单服务故障会阻断验证。必须采用
异步计量、幂等账本和补偿；验证结果先完成，账单稍后重建。预算预检可以阻止新调用，但不能
修改已经产生的证据。

### 风险七：仓库文本 Prompt Injection

README、注释、Issue、测试 fixture 和 schema 可能包含“忽略规则”“上传密钥”“执行命令”等
内容。所有输入分为 instruction/data 两层；只有系统策略和人工批准的任务可以改变动作权限。
工具返回也视为数据，不得直接拼回系统提示词。必须有攻击样本矩阵和真实工具调用审计。

### 风险八：评测集被过拟合

如果所有案例都围绕 demo Spring Boot，Recall/Precision 会高估。需要按契约族、语言、
框架、代码风格、等价重构、预存缺陷、环境噪声和攻击文本做分层 holdout，并定期更换隐藏
案例。发布数字必须同时给出样本数、分布、版本和原始结果。

### 风险九：长期数据无法删除或导出

证据中可能包含私有代码、日志、数据库快照和模型输出。必须为每种数据定义保留期、租户
所有权、删除传播、备份删除、对象生命周期、审计留痕和导出格式。删除证据后证书应进入
“不可验证/已撤销”，不能继续显示为有效。

## 十一、研发治理规则

### 11.1 单一变更原则

每轮只完成一个可验证纵向切片。先写数据契约、权限矩阵、错误路径、指标和测试，再改代码。
不在同一轮同时换框架、改状态机、迁移数据库和重做前端。任何跨边界变更先写 ADR，说明
兼容、迁移、回滚和证据影响。

### 11.2 不自动扩大权限

默认不读取宿主机环境、不读取 `.env`、不访问 Docker Socket、不访问任意网络、不修改默认
分支、不自动 push、不自动创建镜像、不自动运行 Windows 安装包。用户明确授权后才做相应
外部操作；用户没有授权时只做代码、测试、报告和本地可逆验证。

### 11.3 诚实降级

每个依赖都有三档或四档状态：可用、部分可用、不可用、未配置。降级必须在 API、UI、MCP、
日志和报告中显式显示原因、影响和恢复方式。没有 LLM 时可以确定性运行；没有 ES 时可以
BM25 或无检索；没有容器时可以 local fallback，但必须标注隔离等级；没有真实 DB 状态时
不能生成 DB evidence。

### 11.4 版本与发布

发布版本同时绑定代码 SHA、Contract registry 版本、checker 版本、执行镜像 digest、Provider
profile、数据库迁移版本、前端构建摘要和证书 schema。升级先跑兼容矩阵和回放样本；降级要
保留旧证书验证能力。Git 提交、镜像、公共发布、远程推送都不属于默认研发动作，只有在
明确指令下执行。

### 11.5 文档同步

每次架构改动必须同步：架构地图、完成度地图、Go/No-Go、运行指南、故障手册、OpenAPI、
事件 schema、数据字典和评测记录。文档分为“代码存在”“本机通过”“真实基础设施通过”、
“多机/生产未验证”和“规划中”五类标签。禁止只更新销售口径而不更新缺口表。

## 十二、最终验收清单

### 产品闭环

- 用户可以从 CLI、Web、MCP 和 GitHub 发起同一类 Verify Job。
- Job 创建、排队、执行、取消、失败、恢复、过期和终态都可查询。
- 需求可以生成候选 Contract，Contract 可以批准、拒绝、撤销、版本追踪。
- 每条 Contract 都能看到实验、结果、证据、降级原因和回放入口。
- 严重 Finding 没有真实证据时不会升级或签发。
- Capsule 可以在干净环境重放并生成 replay record。
- 证书可以离线验证摘要、签名、工具链和撤销状态。

### 开发 Agent 闭环

- 任务能生成结构化计划并等待批准。
- 工具有权限、参数、预算、超时、输出限制和审计。
- 编辑是原子、可回滚、可检测 stale、可看到 Diff。
- 测试、自校验、独立验证和修复循环有明确边界。
- 取消、崩溃、预算超限和 STUCK 能恢复或人工接管。
- 不自动推默认分支，不自动绕过 SpecProof。

### 安全与隔离

- 无真实凭据进入代码、日志、Prompt、Capsule、报告和评测快照。
- 租户、用户、角色和对象访问有自动化测试。
- Webhook 验签、重放保护、限流、路径校验和错误脱敏通过。
- 沙箱默认非 root、无网络、资源受限、无宿主秘密和无 docker.sock。
- Prompt Injection、恶意构建脚本、符号链接、输出洪水和缓存投毒有测试。

### 可靠性与运维

- Outbox、RabbitMQ、Redis、Mongo checkpoint、MinIO 对象链和 MySQL 状态机有真实故障演练。
- Worker kill 后能按 checkpoint 恢复，且不会重复副作用。
- SSE 断线重连不会丢事件或无限重复。
- 数据库迁移可空库安装，备份可恢复，删除和导出可执行。
- 观测覆盖队列、Worker、Provider、沙箱、证据、对象、数据库、证书和账单。

### 评测与商业

- Golden、holdout、负样本、跨语言和攻击样本有清晰分层。
- Recall、Precision、归因、回放、成本、延迟和恢复率都有原始结果。
- 用量账本可重建，预算和配额可解释。
- 发布前至少完成一次恢复演练和一次安全响应演练。
- 对外材料只使用已证实数字，并标明样本、时间和环境。

## 十三、最终判断

`D:\experim` 里最有价值的不是某一段 prompt，也不是某个漂亮页面，而是已经形成的产品
边界：写代码的 Agent 与验收 Agent 不应是同一个信任角色；严重结论必须绑定可执行证据；
证据必须能够重放；失败和不确定性必须被保留；数据、权限、成本和运维都必须能解释。

当前项目已经从 Phase 0 的“鉴权回归演示”走到了一个相当完整的验证与开发平台雏形，
但也因此进入最容易失控的阶段：功能多、分支多、入口多、历史摘要多，任何一处事实模型
漂移都会削弱可信度。后续最重要的工作不是继续给产品加一个新名词，而是把 Contract、
Experiment、Evidence、Job、Artifact、Certificate、Tenant 和 Usage 这些领域对象冻结下来，
让所有入口围绕同一内核工作，再用全量回放、故障演练和隐藏评测证明系统没有自欺。

终极目标可以浓缩成一句话：

**SpecCraft 负责让 AI 更快地产生可审阅的变更，SpecProof 负责让任何人都能用独立、可重放、
可签名的证据判断这次变更是否值得合并；平台最终交付的不是“模型说通过”，而是“事实链
证明了什么、没有证明什么，以及下一步由谁决定”。**

后续执行顺序固定为：主线治理 → 领域内核 → 证据回放 → 动态实验 → 沙箱与恢复 → 计费与
企业安全 → SpecCraft 闭环 → 生态扩展。每完成一阶段，必须更新完成度地图和 Go/No-Go；
未达到出口条件就停在当前阶段，不用宣传口径掩盖技术缺口。

## 十四、实现级任务拆解：把终极目标落到每个目录

前面的路线解决“先做什么”，本节解决“改哪里、交付什么、怎样判断完成”。每一项都应该
在任务单中写出输入、输出、状态、权限、失败路径、测试和回滚方式。没有这些字段的任务，
即使代码写出来，也只能算探索代码，不能算主线能力。

### 14.1 `agent/` 验证内核

验证内核的第一责任是保持事实单向流动。节点只读取上游已经确认的字段，只写自己的输出，
不能为了方便把整个状态对象重新构造一遍。建议给每个节点定义独立的输入输出模型，并在
图外运行一个状态完整性检查器：要求输入摘要、租户、Job、Contract 版本和执行模式不能
在节点间丢失；要求错误一旦出现只能进入失败或待审路径；要求任何 PASS/FAIL 都能反查
到实验 ID；要求所有临时目录和 worktree 都有清理记录。

`compile_contracts` 要从“返回若干字典”升级为“返回候选集合加编译报告”。编译报告包括
解析规则版本、LLM 是否参与、候选数量、被拒绝的候选、schema 错误、降级原因和需求摘要。
这样用户看到契约少时，能够知道是需求没有表达、解析器没有覆盖，还是模型调用失败，而
不是误以为系统已经判断需求不重要。

`prepare_base` 和 `prepare_head` 要把仓库安全检查单独抽出来。检查项包括路径是否在允许
根目录、提交是否属于仓库、工作树目标是否为空、符号链接是否越界、仓库是否过大、是否
存在禁止文件和是否能在当前执行模式下安全挂载。清理动作不能只依赖正常返回，必须在
异常、取消、超时和进程崩溃后由回收器再次扫描。

`collect_diff` 需要同时产出文件级、符号级和语义候选范围。文件级结果用于审计，符号级
结果用于检索和检查器，语义候选范围用于决定动态实验和变异测试的预算。任何无法解析的
语言或二进制变化都应该保留为“未解析变化”，不能悄悄丢弃。

`run_static_checks` 需要建立检查器注册表和兼容矩阵。注册表字段包括适用语言、框架、
契约族、检查器版本、证据等级、已知误报、预计耗时和是否允许阻断。检查器异常要成为
`CHECKER_FAILED` 证据，而不是把空结果当成没有问题。检查器输出中的路径、行号和符号
必须通过统一规范化函数处理，保证报告、行内评论和 Capsule 指向同一位置。

`generate_counterexamples` 应该拆成生成、审查、编译、注入四个阶段。生成阶段可以使用
LLM，审查阶段检查包名、类名、测试数量、断言是否短路、是否只访问 Head、是否引用不可用
依赖，编译阶段记录命令和输出，注入阶段把同一个文件复制到两个版本并写入注入摘要。若
LLM 连续失败，确定性模板只能在它声明支持的仓库类型上使用；其他仓库必须返回无法生成，
不能套用 Demo 包名。

`run_differential` 需要把“测试运行”与“状态采集”解耦。测试退出码只是一个观察；数据库、
缓存、消息和外部调用各有采集器。采集器缺失时要生成缺证据记录。比较器要支持基线清理、
播种确认、收尾检查和副作用回滚。对同一个实验重复运行时，应能判断结果是稳定、偶发还是
环境污染。

`review_court` 需要把模型三审和确定性政策分层。模型只生产辩护材料和候选置信度，政策层
重新计算严重度和状态。所有被模型忽略的候选要保留在审计中；解析失败不能直接走确认。法院
要增加“预存缺陷”判定：如果 Base 同样失败，默认不归因 Head，除非有新的行为差异。

`build_matrix` 要把契约结果合并规则写成纯函数，并对多个节点的竞争写入做测试。矩阵每行
要带结果来源、实验 ID、证据摘要、最低证据等级、未验证原因和下一步建议。矩阵不是展示
组件的临时数据，而是证书和 API 的共同输入。

### 14.2 `storage/` 数据与可靠性

MySQL 迁移要按领域分组并保持向前兼容。新增列先允许空值，再回填，再加约束；改变枚举
状态时先让旧 Worker 能读取；删除字段要经过至少一个发布周期。每次迁移都要有空库安装、
旧版本升级、新版本回滚或明确不可逆说明。测试不能只验证 SQL 能执行，还要验证旧数据在
新代码下能正确投影。

Job 表应保存输入摘要、租户、仓库、Base/Head SHA、策略版本、Contract 版本、执行模式、
预算、状态、重试次数、Worker、开始结束时间、终态原因和摘要引用。Finding 表保存契约、
严重度、置信度、状态、归因、证据包、Capsule、豁免和审阅人。不要把完整日志塞进 MySQL；
大对象只保存对象元数据。

Outbox 表要有事件类型、聚合、租户、有效载荷摘要、发布次数、最后错误、下次重试时间、
发布时间和死信状态。Relay 必须使用锁和批次，发布成功后再标记；重复发布由消费者幂等，
不能假定“只会一次”。Relay 的指标包括待发布数量、最老事件年龄、失败率、重试次数、
死信数量和最近成功时间。

RabbitMQ 消费者要把“收到消息”“通过幂等检查”“开始处理”“业务写入完成”“Ack”“Nack”
作为可观测事件。业务写入失败时不能先 Ack；处理完成但 Ack 丢失时，重投消息应由幂等键
阻止重复副作用。DLQ 中的消息要能关联原 Job、事件、错误分类和重放次数，不能只是一个
无法解释的 JSON 堆。

Redis 的租约续期要有最大持有时间和 Worker 心跳。租约丢失后，旧 Worker 必须停止写业务
结果；进度 Stream 要有最大长度、保留时间和消费者断点。预算扣减要原子化，失败时要有冲正
或明确“已预留未消费”状态。Redis 丢失后可以重新建立锁和进度，但不能把 Redis 当作恢复
业务事实的唯一来源。

MongoDB checkpoint 要包含图版本、状态 schema 版本、节点名、输入摘要、输出摘要和保存时间。
升级图结构时，要定义旧 checkpoint 是否可迁移；不能因为节点名字改变就静默从头执行，导致
重复外部副作用。Evidence Pack 使用唯一的 Job+Contract+版本键，更新采用新版本文档或
append-only 事件，避免覆盖历史证据。

MinIO 对象命名要带租户、仓库、Job、类型和版本，禁止把用户传入的文件名直接作为对象路径。
上传返回 digest、大小、媒体类型和版本；下载前做权限检查，下载后可选做 digest 校验。
对象生命周期按数据分类配置，Capsule 和证书的保留期不能与临时日志相同。

Elasticsearch 只做投影。索引文档必须包含租户、仓库、提交和来源类型；删除仓库或租户时要
能按过滤条件清理。索引失败不阻断已经有证据的验证，但要把 retrieval degraded 写入结果，
防止用户误以为模型看到了完整仓库。

### 14.3 `api/` 与 `services/control-plane/`

控制面接口必须先画权限矩阵再写路由。对于每个端点，列出匿名、租户 Viewer、Member、
Reviewer、Admin、Owner 的行为；越权时是否返回 404 还是 403；是否记录审计；是否需要
幂等键；是否允许重试；是否返回对象 URL；是否触发异步事件。这个矩阵要与单元测试和
OpenAPI 文档同步。

Job 创建接口不能接受任意命令、任意环境变量、任意 Docker 参数或任意输出路径。用户只能
选择受支持的仓库、引用、策略和验证深度。自定义执行参数必须经过白名单和租户策略，
否则很容易把“验证平台”变成远程执行平台。

错误 Envelope 需要区分客户端错误、权限错误、资源不存在、状态冲突、依赖降级、执行失败、
内部错误和限流。错误响应保留兼容的 `detail`，同时包含稳定 `code`、`message`、`request_id`、
`retryable` 和 `schema_version`。日志不能把原始 Authorization、Cookie、API Key、需求全文
或敏感数据库值直接写入。

SSE 事件要有序列号、事件类型、Job、阶段、状态、百分比、消息摘要和时间。客户端断线时
带 Last-Event-ID；如果事件已经因保留策略删除，服务返回需要重新拉取任务快照的事件，
不能假装已经补全。终态事件必须可重复消费，前端收到重复终态不应重复弹窗或改变状态。

Spring Control Plane 若继续保留，建议只承担组织级事务、Webhook 验签、审计和可靠投影，
不要与 FastAPI 同时写同一套 Job 状态。两者通过事件和共享 schema 协作；迁移、权限和错误
码统一。若未来团队规模较小，优先把它收敛为独立集成模块，减少双控制面的运维负担。

### 14.4 `apps/web/` 前端工作流

前端的验收标准不是页面数量，而是用户能否完成闭环。验证向导要在第一步就显示仓库、
Base、Head、需求、预计耗时、执行模式和权限；提交后显示队列、Worker、当前阶段和取消按钮；
详情页显示矩阵、Finding、证据、回放、证书或拒绝原因；任何降级都显示影响范围和建议行动。

Agent 页面要显示计划状态、审批按钮、每个工具调用、修改文件、测试结果、五道门、预算和
取消；不要把模型的长思考内容作为主要 UI。用户应能折叠原始输出、查看摘要、定位文件和
下载审计。无 LLM 时的确定性流程应同样完整，不能因为没有 Key 就出现空白页。

权限页面要能解释当前租户、角色、来源和失效时间；权限拒绝显示可操作的联系管理员提示。
健康页面要分别显示“服务可达”“依赖可达”“能力完整度”“当前降级”和“数据是否可查询”，
不要把一个总体绿色图标覆盖所有缺陷。

### 14.5 `providers/`、`retrieval/` 和 `craft/`

Provider 的所有网络调用都要经过统一客户端，配置只来自环境或秘密管理器。每次调用记录
模型、能力 profile、超时、重试、token 估算和结果类型；原始请求正文不进入普通日志。工具
调用失败时要记录错误分类和是否可重试；HTTP 400 不应无限重试，429/5xx/超时按退避处理。

检索结果要有来源路径、提交、行号、符号、命中方式和分数；上下文拼装要限制总字符和文件
数量。仓库中出现的规则文件应以数据形式加载，规则优先级由系统定义。对注入文本的检索
命中要有测试，确认它不会改变工具权限或系统目标。

Craft 工具注册表要给每个工具分配稳定名称、版本、参数 schema、风险等级、成本函数、
允许状态、可取消点和审计字段。编辑器继续保持唯一替换、stale digest 检查、原子写、备份
和审计；未来 AST 编辑应作为新工具版本加入，不要悄悄改变旧工具的替换语义。

## 十五、典型业务场景的逐步验收样例

### 15.1 鉴权注解被移除

需求要求未登录用户不能修改邮箱。Contract 编译为 AUTH-01，适用符号是用户邮箱修改接口，
最低证据为 HTTP 401/403 和数据库不变。Base/Head 准备完成后，静态检查发现 Base 有
`@PreAuthorize` 而 Head 没有，生成 MAJOR 候选；动态模板在两边创建同一用户，发送同一未
认证 PUT。Base 返回 401 且用户邮箱不变，Head 返回 200 且 H2 行变为攻击者邮箱。差分
结果记录退出码、响应、数据库快照、测试摘要和 digest。法院校验六条件后确认 BLOCKER，
矩阵把 AUTH-01 标为 FAIL，Capsule 包含测试和回放脚本，Job 终态为 BLOCKED。

如果 Base 和 Head 都返回 200，系统不能说“Head 回归”，而应显示预存缺陷或测试环境问题；
如果两边都返回 401 但 Head 静态注解变化，最多是静态 MAJOR；如果 H2 文件缺失，HTTP 证据
仍可成立，但数据库条件为未满足，严重度不能凭空升级。

### 15.2 事务边界被拆开

需求要求更新邮箱、失效旧 Token、发布事件具有一致性。Contract 包含 TRANSACTION、TOKEN、
EVENT。动态模板先播种用户和 Token，再让更新操作在中途抛出异常；比较 Base/Head 的数据库、
Redis 和消息状态。若 Head 数据库更新成功但 Token 未失效，或者消息发布而事务回滚，系统
要分别生成状态观察和影响路径。静态失去 `@Transactional` 只是候选，不足以证明具体副作用。

如果 RabbitMQ 在本地测试中被排除，报告必须写清 EVENT 没有被验证，而不是把“代码调用了
convertAndSend”当作 PASS。若数据库和 Redis 都没有状态采集器，矩阵应显示 UNVERIFIED，
并给出下一步需要启用的实验模板。

### 15.3 重复事件和错误 Routing Key

需求要求一次邮箱变化只发布一条事件，且 routing key 必须为 `email.changed`。探针在 Base
和 Head 执行同一请求，记录 publish_count、exchange、routingKey、payload、timestamp 和
failed。Head 发布两次时，事件数量差异为回归；Head 只把 routing key 改成 typo 时，数量不
变但语义字段差异为回归。消息断言失败不能只依赖应用日志，应由探针工件或测试替身提供
机器可读证据。负样本中等价的 exchange 配置、注释变化和消息字段顺序变化必须不产生 Finding。

### 15.4 SpecCraft 修改一个计算函数

用户提交任务和仓库规则，Agent 解析后生成七步计划，列出将读取的文件、可能修改的函数、
测试命令和预算。用户批准计划，Agent 只读搜索并读取目标，执行唯一匹配编辑，运行测试。若
测试发现整除判断反了，诊断步骤引用失败输出，生成最小修复，重新运行测试和五道门。Craft
Job 进入 HANDOFF_VERIFY，SpecProof 对 Base/Head 运行独立检查。若验收通过，用户看到 Diff、
测试、矩阵和证书；若失败，用户看到 Capsule 和修复建议。任何模型“我已经修好了”的文本
都不会改变终态。

### 15.5 Worker 在差分执行中崩溃

Job 已从 RUNNING 进入 `run_differential`，MongoDB 保存了前一节点 checkpoint，Redis 租约
过期。新 Worker 获取租约后使用同一 thread_id 恢复，从差分节点继续。若旧 Worker 实际已经
完成一部分外部副作用，实验必须使用幂等 fixture 或独立工作目录，避免重复修改。恢复后
Job 只能有一个终态，Outbox 和进度事件重复消费不产生两份 Finding。报告要记录崩溃、接管、
恢复节点和最终证据是否来自同一次实验。

### 15.6 Capsule 在另一台机器回放失败

回放程序先检查 Java/Maven/容器/缓存和仓库引用，再执行临时 worktree。若失败原因是缺少
工具链，记录环境不匹配；若脚本路径穿越或对象摘要不一致，判定 Capsule 损坏；若同一工具链
下 Base/Head 结果不同，判定证据不稳定或产品缺陷。系统不能把所有失败都显示为“业务回归
仍然成立”，也不能因为原报告曾经通过就跳过当前验证。

## 十六、长期决策原则

第一，先证明再扩展。新契约、新模型、新适配器、新页面都必须先有最小验收和失败样本。
第二，结果可追溯。任何用户看到的数字都要能反查到 Job、版本、命令、工件和原始输出。
第三，失败有分类。系统故障、代码回归、需求不完整、环境不足、权限拒绝和预算超限不能
混成一个红色数字。第四，默认最小权限。所有工具、网络、文件和租户访问都从拒绝开始。
第五，状态不可伪造。没有执行就是未验证，无法采集就是缺证据，模型失败就是失败或降级。
第六，局部可替换。Provider、检索、执行器、存储和入口都通过小而明确的协议连接，避免
改一个适配器就重写全链路。第七，先本地流畅再谈规模。用户已经明确不希望每轮都跑安装
包和镜像线，近期以本机可点完的确定性流程、可复核报告和快速回归为第一优先级。

以上原则不是口号，而是排期过滤器：任何不能增加可信度、可复现性、可操作性或安全边界
的复杂度，都应该推迟；任何会降低现有证据诚实性的“快捷演示”，都应该拒绝。

## 十七、每周工作循环与管理节奏

为了避免项目再次出现“多个副本各自向前、最后靠复制文件合并”的情况，研发过程需要有
固定节奏。每周不是简单按照日历切一块功能，而是完成一次可复核的证据闭环。

周一做审计。先查看主线状态、未提交改动、迁移、依赖、失败测试、未关闭告警和上一周的
评测结果。审计输出不能只写“代码基本正常”，而要列出新增能力、受影响 Contract、风险
边界、预计命令和不做事项。发现工作树有其他人正在修改相关文件时，先保存当前事实并在
同一文件上协作，不得通过强制回滚清除未知改动。

周二做契约和测试设计。把目标行为写成输入、前置、操作、观察、期望和失败分类；先补正样本、
负样本、holdout 或故障样本，再选择实现位置。任何声称提升 Recall 的改动，必须先在测试中
证明过去漏检的案例，否则很可能只是增加了没有实际价值的代码量。

周三到周四做一个纵向切片。代码、迁移、API、报告、前端、脚本和测试一起完成最小闭环，
不允许只写底层适配器然后把“以后接起来”当作完成。涉及 LLM 时先用 mock 和确定性模式
验证结构，再在用户允许且有安全凭据时做真实端点验证。涉及外部基础设施时，只启动已有
服务，不擅自构建镜像、发布网络服务或修改机器级配置。

周五做验证。先跑受影响的聚焦测试，再跑契约子集、集成子集、静态检查、类型检查和安全扫描。
如果全量测试预计很久，先报告聚焦结果和预计耗时，再根据用户指令决定是否继续；不能让一条
长测试占住会话而没有状态更新。Windows 安装包、Docker 镜像、远程推送和公网探针必须作为
显式任务单独执行，不要因为“顺手验证”改变工作范围。

周末或里程碑前做复盘。更新完成度地图、Go/No-Go、运行指南、变更日志和风险清单。对外数字
必须从原始结果文件重新生成；如果某项以前 PASS 现在无法重跑，标为“历史证据、当前待复核”，
而不是继续保留绿色状态。这样做会让数字短期看起来变少，但长期能显著提高可信度。

## 十八、发布前后的实际操作手册要求

发布前必须有一份不依赖作者记忆的操作手册。新机器从零开始时，读者应能知道需要哪些版本、
哪些端口、哪些环境变量、哪些凭据、哪些服务、哪些目录、预计耗时和成功输出。手册要同时
提供无 LLM 的确定性流程，让用户在没有模型 Key 时仍能验证本地系统是否工作。

启动顺序建议是：先检查 Python/Node/JDK/Docker 版本，再检查端口和目录权限；然后启动本地
基础设施或使用已有服务；等待健康检查；加载非敏感种子；启动 API、Worker、Outbox Relay 和
前端；最后执行健康、契约、Demo Verify、Capsule inspect 和 UI 冒烟。每一步都必须有明确的
停止和清理命令。任何命令会删除卷、清除数据库、修改当前分支或覆盖工作树时，都要在标题中
标出破坏性影响，并要求用户确认。

故障章节至少覆盖：端口占用、依赖未就绪、Maven 缓存缺失、JDK 版本不符、Provider 429/401、
LLM 能力不足、ES 不可用、RabbitMQ 重投、Worker 无法获取租约、SSE 断线、Capsule 找不到、
证书摘要不一致、前端资源过期和数据库迁移失败。每种故障都要说明“是否影响业务事实、是否
可以重试、是否需要清理、是否需要轮换凭据、是否需要人工介入”。

备份章节要说明 MySQL、MongoDB、MinIO、Redis 和 Elasticsearch 的不同定位。MySQL 备份是
业务事实和审计的主要恢复来源；MongoDB 要备份 checkpoint 和 Evidence Pack；MinIO 要备份
对象及元数据；Redis 可重建但要记录丢失的进度影响；ES 可以从源数据重建。恢复后必须重新
跑对象链校验、Job 投影校验、权限校验和一份 Capsule replay，不得只看服务能否启动。

升级章节要包含兼容窗口、迁移顺序、回滚条件、旧证书验证、旧事件消费、前端 API 版本和
旧 Capsule 回放。回滚不是把代码恢复就算完成，还要检查迁移是否已经改变数据、Outbox 是否
有新版本事件、对象是否使用新 schema、缓存是否需要清空以及正在运行的 Worker 是否应该
排空。若迁移不可逆，发布说明必须提前写清楚，不得用“支持回滚”笼统描述。

## 十九、面向不同用户的价值链路

对于个人开发者，最重要的是无需搭建复杂平台即可在本地运行一次真实验证。CLI 应该用清晰
的阶段输出告诉他：需求识别了几条 Contract，哪些实验运行了，哪里证据不足，是否生成了
Capsule，是否需要人工决定。个人用户不需要先理解 MySQL、MongoDB、RabbitMQ 的职责，但应
能在报告中看到这些依赖是否参与，从而知道结论范围。

对于小团队，重点是 PR 阻断和可重放。GitHub Check 应显示阻断原因、Contract、严重度、证据
类型和 Capsule 链接；团队成员可以在本地或 CI 重放，不必相信某个模型的长评论。Contract
审批要有轻量流程，允许把项目约束逐步沉淀为规则，而不是第一次就要求建立完整企业治理。

对于企业私有部署，重点是租户、身份、数据驻留、审计、密钥、备份和成本。企业客户关心的
不是首页有多少按钮，而是私有仓库是否会跨租户泄露、模型调用是否可控、证据是否能在审计
时复核、证书是否能由内部公钥验证、员工离职后权限是否立即失效、删除请求是否传播到备份。

对于编码 Agent 平台，重点是 MCP 和 API 的稳定协议。外部 Agent 只需要调用少数几个工具，
拿到结构化验证摘要、契约状态、健康降级和 Capsule 信息；它不应该读取内部数据库、猜测
报告文件名或执行任意命令。MCP 的价值在于把独立验收能力嵌入任何开发 Agent，而不是把
SpecProof 变成另一个需要用户学习复杂内部结构的框架。

对于审计、合规和安全团队，重点是证据血缘和不可抵赖。审计人员应能从证书反查需求、审批、
提交、实验环境、工具输出和回放记录；能区分模型意见、静态发现、动态观察和最终政策判决；
能看到谁在什么时间批准了 Contract、豁免了什么 Finding、使用了哪个签名密钥。系统必须允许
审计人员只读访问证据，而不授予执行代码或修改结论的权限。

## 二十、为什么这条路线比继续堆功能更稳

第一，证据链优先会迫使所有新功能说明自己产生什么事实、写入哪里、如何重放。这样可以
防止“页面先上线、后端再猜数据”的漂移。第二，领域内核优先会让 CLI、API、MCP、Web 和
GitHub 的行为一致，减少一个入口修了另一个入口仍旧错误的情况。第三，回放和故障优先会
暴露环境依赖、时间随机性、重复副作用和缓存投毒，这些问题通常比单次 happy path 更接近
真实生产事故。第四，契约和评测优先会把“模型看起来很聪明”转化为可测量的发现率、归因率、
误报率、成本和恢复率。第五，本地优先符合当前用户的实际要求，能在不构建安装包、不发布
镜像、不做远程部署的情况下持续提高产品质量。

相反，如果现在继续并行开发更多语言、更多页面、更多 Agent 子代理、更多计费套餐和更多
模型路由，短期演示会更丰富，长期却会产生更多状态、迁移、权限和失败路径。没有统一事实
模型时，功能越多越难判断哪个结果可信；没有全量回放时，证据越多越难判断是否稳定；没有
明确发布边界时，实验副本越多越容易把草稿当主线。稳健的终极路线不是追求模块数量，而是
让每个新增模块都能被相同的事实、权限、证据、评测和运维框架约束。

## 二十一、最终交付形态的想象

用户打开本地系统后，首先看到的是当前租户、依赖状态、可用执行模式和最近任务，而不是
营销口号。点击“新建验证”，系统让他选择仓库和提交，粘贴或选择需求，展示候选 Contract、
执行深度、预计耗时和预算。用户批准后，页面实时显示每个阶段，任何降级都给出影响说明。
完成后，矩阵按需求展示通过、失败、未验证和证据链接；Finding 显示代码位置、Base/Head
行为、状态差异、严重度政策和 Capsule；证书页面显示摘要、签名、公钥版本、工具链和验证
结果。用户可以复制一条无破坏性的 replay 命令在另一个工作目录验证，也可以把结构化结果
交给外部 Agent。

如果用户进入 SpecCraft，页面先显示计划而不是直接改代码。计划指出目标、文件、命令、风险、
禁止操作和预算。用户批准后，工具流按时间线显示，编辑提供前后对照，测试和门禁结果可展开，
取消和恢复都可操作。Craft 完成后，系统自动把变更交给 SpecProof；即便 Craft 自己显示全绿，
只要独立验证发现回归，最终状态仍是 BLOCKED 或 NEEDS_REVIEW。这个交互要让“写代码的不能给
自己签字”成为用户看得见、点得着、无法绕过的产品行为，而不是只写在架构文档里的理念。

从运维角度，管理员能看到队列、租约、Outbox、Provider、沙箱、对象、数据库、证书和账单的
健康与 SLO；能暂停新任务、轮换凭据、撤销证书、清理过期对象、重放死信和恢复备份。从审计
角度，任何重要动作都有不可篡改或可检测篡改的记录。从研发角度，每次变更都能通过聚焦测试、
评测子集和全量门禁判断是否改善或回退。产品、用户、运维和研发看到的是同一套事实模型，
只是投影和权限不同。

这就是本项目值得持续演进的终极形态：不是把更多 AI 接进来，而是把 AI 产生的变化放进一条
可观察、可限制、可复现、可争辩、可签发、可撤销的工程链路。只有当用户能够相信系统说出的
“通过”“阻断”“未验证”和“无法复现”分别意味着什么，SpecProof 才真正从实验项目变成可信
基础设施。

还要特别强调一条长期纪律：任何阶段都不能用一次漂亮演示替代持续测量。旗舰案例可以
说明链路打通，却不能代表所有语言、所有数据库、所有并发条件和所有团队流程都可靠。每个
里程碑都要同时保存成功样本、失败样本、边界样本和环境失败样本；每次模型、解析器、执行器、
沙箱、存储或前端升级都要重跑受影响的样本。这样，项目的成长不是靠叙事不断变长，而是靠
证据空间不断扩大、未知范围不断缩小、失败分类不断清晰、恢复路径不断可执行。最终用户
获得的也不只是一个“能跑”的工具，而是一套在需求变化、模型变化、代码变化和基础设施
变化之后仍然能够说明事实边界的工程制度。
