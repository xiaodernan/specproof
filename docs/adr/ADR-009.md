# ADR-009 — 为什么 Mutation 只跑影响范围

状态: 已接受 (2026-08; P4 实现为模块级范围, diff 级范围未接入)

背景: 变异测试回答"测试到底有没有用": 一个验证器没发现的回归, 可能
是因为没有任何测试会因它失败。全仓库全算子变异在成本上不可行 —
每次变异都要重跑测试。

决策: 变异只跑影响范围 (PRODUCTION_SPEC §22 ADR-009), 且只在 DEEP
tier 运行 (agent/nodes/run_deep_experiments.py)。实现机制
(experiments/mutation.py):
- 范围 = HEAD 工作区应用模块的主源码: src/main/java 下全部 Java 文件,
  跳过测试文件与 target/; 每个文件变异体上限 max_mutants=10
  (DEEP 节点) / 20 (函数默认), 四类文本级算子 (移除注解、布尔翻转、
  删除 null 检查、return 翻转);
- 每个变异体只跑一条测试 — 生成的反例测试 (generated-tests), 通过
  sandbox 执行 (mvnw test), exit 0 = SURVIVED, 非 0 = KILLED;
- 存活变异体只报告为 TEST WEAKNESSES, 绝不当作 Bug Finding。

理由: 变异价值在于暴露测试弱点, 而不是制造更多 Finding; 限定范围 +
单文件上限 + 单测试执行把成本压到可预算; 把"变异只在影响范围跑"
作为纪律, 避免变异测试退化成全仓回归跑批。

后果与局限: 当前"影响范围"是模块级 (整个 app 的主源码), 尚未接入
collect_diff 的 changed_files 做文件级缩小 — 对大型仓库会过宽;
算子是文本级的 (正则), 不做 AST 编译校验, 等价变异体
(如翻回等价布尔) 可能存活; 变异报告落在 deep-report.json 与
MutationReport.to_dict() 中。

对应 PRODUCTION_SPEC: §22 ADR-009; §11 后端语义验证。
