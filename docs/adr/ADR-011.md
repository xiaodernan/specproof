# ADR-011 — 为什么 Certificate 绑定需求版本和 Commit

状态: 已接受 (2026-08; P5 已实现 Ed25519, 取代旧 ADR-009 的
"SHA-256 digest 而非签名" Phase 0 策略, 该旧文见
LEGACY-ADR-000-010-combined.md)

背景: 一张不绑定"验证的是什么"的证书毫无意义 — 需求改了、Commit 变了,
旧证书都不再适用; 而只用 SHA-256 digest 只能证明内容未被篡改
(且需要信任通道), 不能提供签发人身份与不可抵赖, 把一个 digest 叫做
签名是安全产品的信用问题。

决策: Merge Certificate (evidence/certificate.py) 的 subject 绑定
repository + commit_sha, 并记录 requirements_digest (需求文本的
sha256)、evidence_digests (证据摘要链) 与 toolchain (specproof_version/
python); 只有全部 Contract PASS 且证据齐全才签发证书, 否则签发
RejectionNotice (证书的缺席本身就是结论)。P5 起由 evidence/signing.py
叠加 Ed25519 签名: 载荷经规范序列化 (sort_keys) 后签名, 输出
in-toto 风格 statement (_type/subject/payload/signatures, keyid =
公钥 sha256 前缀), verify_statement 可离线验签。

理由: 需求版本 + Commit + 证据摘要 + 签名四个要素绑定后, 证书成为
"在哪个提交上、针对哪份需求、基于哪些证据、由谁签发"的完整声明,
可离线验证、不可抵赖; 签名密钥不在源码中 (SPECPROOF_SIGNING_KEY /
SPECPROOF_SIGNING_KEY_FILE, fail-closed)。

后果: 未配置签名密钥时回退为无签名摘要并明确记录 (文档化降级,
绝不假装签名); digest 与 signature 的命名规范沿用旧 ADR-009 的
"digest 不是签名"原则, 命名分界写入证据政策; 证书字段按 in-toto
Statement 风格演进, 为 Phase 2 的完整证明链预留。

对应 PRODUCTION_SPEC: §22 ADR-011; §0 安全前置。
