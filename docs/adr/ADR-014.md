# ADR-014 — 为什么自动修复需要审批

状态: 已接受 (2026-08; P5 实现)

背景: 验证器发现的问题不应被同一个系统擅自"修好"再合并 — 自动改码
会把验收防火墙变成又一个不受控的代码生成器; 但完全不给修复能力又
浪费了验证器手里的 Base/Head 精确差异。

决策: 修复分两步, 中间必须有人的审批 (cli/specproof/commands/fix.py):
1. specproof fix — 只提案、不落盘: agent/fixes.py 仅对"机械还原 Base
   行为且 diff 锚点可精确匹配"的四类场景生成确定性补丁 (恢复被删
   注解 AUTH-01/TRANSACTION-01/OPENAPI-01、恢复 token 失效调用、
   移除重复事件发布或恢复 Base 发布行、恢复校验注解 UNIQUE-01),
   其余一律 skipped + 原因, 绝不编造补丁;
2. specproof approve FIX_ID — 应用 + 验证: apply_fix 带锚点漂移守卫
   (Head 行内容与提案时不一致则拒绝应用), 应用到全新 Head worktree,
   并要求 Maven 编译 EXIT=0 才报成功; 无法编译则标记
   applied_unverified 且退出码 1; --github 发布为 best-effort,
   无凭据时把 PR payload 落盘而不是假装已推送。

理由: 自动修复的每一步都可以被拒绝或漂移, 审批 + 编译门把"自动改码"
关进笼子里; 确定性补丁 (而非 LLM 生成补丁) 保证提案可解释、可复核。

后果: 只有机械可还原的问题有修复提案; 复杂问题仍需人工处理;
审批动作记录 FIX_ID 与验证结果, 支持审计。

对应 PRODUCTION_SPEC: §22 ADR-014; §6.2 PR 命令。
