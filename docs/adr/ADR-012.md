# ADR-012 — 第三方 OpenAI-Compatible 网关兼容策略

状态: 已接受 (2026-08)

背景: 第三方网关普遍"部分兼容" — 有的没有 tool_calls, 有的
strict_tool_calls 直接 400, 有的 thinking 与工具互斥。假设完整兼容
会在生产随机失败且难以定位 (DeepSeek gateway 实测: strict_tool_calls
返回 HTTP 400, reasoning_content 始终返回, 已由 JSON Action Envelope
降级处理)。

决策: 任何新网关先跑 10 维能力探测 (providers/capability_probe.py):
/models 可达性、Chat、Streaming、JSON Output、Tool Calls、Strict Tool
Calls、Thinking、Thinking+Tools、Usage、错误码与限流头; 探测结果
(ProbeResult) 决定降级路径 (providers/openai_compatible.py):
- tool_calls 不可用 → 工具定义注入为 system prompt, 要求模型返回
  JSON Action Envelope {"action": ..., "params": ...};
- json_output 不可用 → 不发 response_format, 调用方按信封解析;
- thinking 不可用/不稳 → 计划与判断用思考、工具循环不用
  (extra_body 仅在能力允许时附加);
- 探测在首次 API 调用时惰性执行 (lazy probe), 结果进程内缓存。

理由: 探测 + 显式降级把"网关部分兼容"从随机故障变成可预测、可记录
的行为; 每条降级路径都在 Provider 层完成, 业务节点不感知网关差异。

后果与局限: probe 结果进入 Job 记录由调用方负责 — 当前实现只做
进程内缓存与 CLI 输出 (specproof probe), provider_capabilities 的
MySQL 持久化尚未落地; 对每个新网关都必须先跑探测, 不能默认其
完整兼容。

对应 PRODUCTION_SPEC: §22 ADR-012; §8 能力探测 10 项。
