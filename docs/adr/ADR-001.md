# ADR-001 — 为什么不是普通 Code Review

状态: 已接受 (2026-08)

背景: 市场上已有大量"AI 给代码提意见"的产品, 输入 Diff 与仓库上下文,
输出评论、风险与修复建议; 大部分结论依赖模型判断, 无法验证真伪,
"测试通过"也不等于"需求完成"。

决策: SpecProof 不是 Code Review Bot, 而是验收防火墙: 输入 Requirement +
Acceptance Criteria + Forbidden Changes + PR, 输出每一条需求对应的
**可执行证据** — Requirement-to-Evidence Matrix (evidence/report.py)、
Base/Head 差分执行结果 (agent/nodes/run_differential.py)、可重放
Bug Capsule (agent/nodes/create_capsule.py) 与 Merge Certificate
(evidence/certificate.py), 而不是意见与建议。

理由:
- 评论无法验证真伪, 证据可以重放 (capsule 内 run.sh/run.ps1 一键复现);
- 实现 Agent 与验证 Agent 必须隔离, 否则是自签自证 (见 ADR-003);
- "测试通过 ≠ 需求完成" — 只有对照需求逐条验证才有意义;
- 差分执行把结论从模型判断变成事实陈述 (见 ADR-008)。

后果: 高等级 Finding 必须携带可执行证据, 无证据的严重评论视为缺陷
(SLO: 0 容忍, 见 ADR-004); 检测管道必须真实执行测试, 没有执行能力的
结论自动降级; 产品定位与普通 Code Review 在输入、输出与判定方式上
完全分开。

对应 PRODUCTION_SPEC: §22 ADR-001; §4 本质差异。
