# ADR-006 — 为什么 Redis Stream 不替代 RabbitMQ

状态: 已接受 (2026-08)

背景: 关键任务消息 (verify.job 等) 需要可靠投递; Redis Pub/Sub 断线
即丢消息, 会把"任务不丢不重"的 SLO 毁掉; Redis Stream 虽然比 Pub/Sub
可靠, 但消费确认、死信与重试语义仍需自建, 且持久化与确认成本不低。

决策: 可靠任务走 RabbitMQ (storage/rabbitmq.py): Publisher Confirm +
Manual Ack + DLQ (.dlq/.retry 队列, QueuePolicy: max_retries=3,
退避 1s/5s/30s) + 幂等消费 (make_idempotency_check, 按 event_id 去重,
x-death 计数识别重投) + Transactional Outbox (storage/mysql.py,
job 与 outbox 同事务落库)。Redis (storage/redis.py) 只做锁/租约/
预算/进度流 (worker lease、LLM token budget、progress stream), 全部
key 带 TTL, 不做任何永久业务状态。

理由: RabbitMQ 的 confirm/ack/DLQ 组合是现成的可靠投递语义; Redis
Stream 的优势在低延迟进度通知, 把"可丢失的实时数据"留给它, 把
"必须送达的业务命令"留给 RabbitMQ, 职责清晰。

后果: 生产拓扑固定 exchange 与队列 (commands/events/dlq), 消息含
trace_id 与 attempt; 重复投递靠幂等消费兜底 (tests/unit/
test_concurrency_ha.py 验证 N 次投递只处理一次); Redis 故障只影响
进度展示与预算, 不影响任务结果。

对应 PRODUCTION_SPEC: §22 ADR-006; §8 所有技术的真实职责。
