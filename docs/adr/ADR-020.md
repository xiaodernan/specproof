# ADR-020 — 为什么配置热刷新走本地 `/actuator/refresh`，而不是 Spring Cloud Bus

状态：已接受（2026-11-13；控制面见证人于 #1646 落地，边缘于 #1650 落地）

背景: #1608/#1609 给 control-plane（Spring Boot）和 edge（Spring Cloud Gateway）都接了本机可选配置中心导入（`optional:configserver:http://localhost:8888`）。"推 config-server → 实例原地换值"这条链缺最后一公里：**刷新信号**。Spring Cloud 的标准答案是 Spring Cloud Bus——一个共享 broker（这里是 RabbitMQ）广播整个 fleet 的刷新。2026-11-13 实测：在这个仓库的离线/受限网络里，Bus 路线走不通——

- 本地 .m2 里 `spring-cloud-starter-bus-amqp` **只有 4.3.2**，而 BOM（2024.0.1）钉的 bus 是 **4.2.1**，本地不存在；
- `mvn -o` 直接拒绝解析：`The POM for org.springframework.cloud:spring-cloud-starter-bus-amqp:jar:4.2.1 is missing ... Cannot access central ... in offline mode`（原文留档）；
- 把 Bus 升到 4.3.2（cloud 2025.x 家族）等于打破"一份 BOM 管全部家族版本"的约定，只为换一个 endpoint；
- 且 Bus 的语义是"一条消息刷全 fleet"——里面藏着运维最容易误判的一跳：消息发了 ≠ 每个实例都刷新了背景环境。

决策: **两台服务各自 `POST /actuator/refresh`**（Spring Cloud 自带的 refresh endpoint，`spring-cloud-context` 已在 classpath，零新依赖），各自带一个 EnvironmentChangeEvent 见证人 bean，计数各自的 meter；**fleet 一致 = 两个 meter 配对读**，不是单一信号：

| 服务 | 端点 | 见证人 meter |
|---|---|---|
| control-plane | `http://8081/actuator/refresh`（app 端口） | `specproof_cp_config_refresh_events_total` |
| edge | `http://8090/actuator/refresh`（管理端口，loopback 绑定，永不上公网） | `specproof_edge_config_refresh_events_total` |

诚实边界（两条都接受，写进 ADR 而不是埋在注释里）：

1. **refresh 重发 Environment，但不重绑任何 @ConfigurationProperties 单例**——edge 的
   GatewayProperties 被过滤器、RouteTableIsomorphismGate、GatewayMqEventConsumer
   构造注入，control-plane 的缓存/熔断器配置同理。刷新后这些 bean 持有旧值，直到重启。
   要真正热绑必须 @RefreshScope 波及面（改构造注入为 lookup 或 @Lazy lookup），
   那是一个独立决定，本 ADR 不做。
2. **见证人不证明 fleet 一致**——它只证明"本实例收到了 EnvironmentChangeEvent"。
   两个 meter 都涨 ≠ fleet 一致（可能是两台不同实例各刷了一次）；fleet 一致需要
   数量证据（全部实例 meter 都对齐到同一 generation），这是运维脚本的职责，不是 bean 的。

理由:

1. 零新依赖——Bus 不带来任何本决策不需要的能力；refresh 端点用 classpath 现有物就能跑；
2. 离线 CI 可复刻——Bus 需要 broker 才能测，refresh 端点真 POST 一次就能测（两条 wiring 腿已落：`ControlPlaneApplicationTests#theExposedRefreshEndpointActuallyRefreshesAndCounts`、`GatewayActuatorRoutesTests#theRefreshEndpointActuallyRefreshesAndCounts`）；
3. 故障语义可辨认——curl 没到（网络/LB）、curl 到了服务没刷（endpoint 未暴露）、事件没发（监听器没注册）三种失败在 meter/架构上分得开；
4. 运维动词简单——`for i in $(seq ...); do curl -X POST localhost:$i/actuator/refresh; done`，再读双 meter 配对。

后果:

- fleet 刷新节奏由操作员（或 LB 循环脚本）逐实例驱动；不做"一条消息刷全 fleet"——那个语义在本网络条件下不存在；
- 将来 BOM 补齐（或家族对齐到 bus 4.2.1/4.3.2）可重新评估 Bus；见证人语义不变（Bus 派发的 EnvironmentChangeEvent 照样被两个 bean 计数），ADR 只改传输层，不改承诺；
- 两份 meter 名称载入 OBSERVABILITY.md 8.10 清单与 RUNBOOK §5 运维条目；两条 wiring 腿作为"端点存在 + meter 移动"的下限绑定——没有它们，"expose 里写了 refresh"仍然是一句话，不是一个测量。

对应 PRODUCTION_SPEC: §17（部署形态）；ADR-018（边缘管理端口）；ADR-019（边缘入向流控）。
